# Pending-participant restore: concurrency assurance

This evidence applies to the board-only `POST /api/issues/{id}/restore-participant` operation. All database experiments used disposable embedded PostgreSQL databases created by the server test helpers; no production card or database was modified. The operation does not repair cards with active recovery actions or pending interactions, and no bulk repair is provided.

## Executed scenarios

Run from the repository root with `pnpm --filter @paperclipai/server exec vitest run <test-file>`:

| Test file / scenario | Observation |
| --- | --- |
| `src/__tests__/issue-restore-participant.test.ts`: happy path, refusals and concurrent requests | Atomic expected-value compare-and-set; one winning assignment and one audit row; status, status version, execution state, pending timestamp, stage and decision history unchanged; no wake; agent and other-company callers refused. |
| Same file: restore-first/recovery-first two-connection pool | Both orderings completed within five seconds when one contender initially waited on an issue or run row. Actual restore route returned 409 on the seeded live native run, recovery claimant fulfilled, assignee and audit unchanged. The assertion detects the first blocked contender while the second is in flight; it does not assert simultaneous blocking. |
| `src/services/native-runtime/native-runner-restart-recovery.integration.test.ts`: inverse row locks | PostgreSQL returned SQLSTATE `40P01` for the direct issue-then-run versus run-then-issue transaction overlap; one transaction rolled back with assignment and run status unchanged. This is a database lock-order experiment, not a claim that the route itself deadlocked in that test. |
| Same file: twenty delayed recovery claims | A held run row remained locked across twenty claim attempts; the test waits 900 ms **before each attempt**, not for a 900 ms lock budget. Each attempt hit two separate 1-second run-row lock timeouts, deferred with a warning and no rethrow; a subsequent explicit pass after release claimed it. Before the deferral fix, the same test rejected on the second `55P03`. |
| `src/__tests__/heartbeat-process-recovery.test.ts`: scheduled native recovery after a held issue row | The startup pass encountered two real PostgreSQL lock timeouts and returned a deferred disposition. Release before the fast retry allowed that retry to claim the run without a manual pass. Holding through all three 1/2/4-second retries persisted one error-level `native.recovery.transition` event (`reason: lock_retry_exhausted`, `retryAttempts: 3`) with coordinator generation and history still unchanged; release **after** the cap let the 5-second periodic retry claim automatically, without another exhaustion event. The successful claim follows the existing `executeRun` dispatch path; these assertions prove claim and bounded retry cadence, not provider completion. |
| `src/__tests__/heartbeat-wake-lock-pool-starvation.test.ts`: held actual restore | In 20 isolated issues, the real Express restore route held the issue row while its activity-log insert waited on a disposable audit-table blocker. The real `heartbeatService.wakeup` for the **new participant** on a one-connection pool waited on that restore row; no run queued before release, then restore returned 200 and the participant wake admitted. This does not establish that the former assignee can wake afterward. The nested-only context retained its `paperclipIssue.id` without adding top-level `issueId` or `taskKey`. |
| Same file: direct held issue row and other wake | Another 20 distinct nested-only wakes serialized against issue rows. An unscoped wake preserved its explicit task key and serialized `executionContext` unchanged. |
| `src/__tests__/issue-restore-participant.test.ts`: post-final-read writer overlaps | The disposable assignment-update trigger paused restore after its final live-run read. Before guards, bounded nested retry, same-scope context rebinding and stale quota escalation each left a run for the former owner while restore returned 200. Two additional bounded-retry reason branches (`max_turns_continuation`, `interaction_continuation_infra_retry`) likewise scheduled an old-owner successor before the shared nested-issue guard was moved ahead of them. After guards, all three retry reasons return `not_scheduled`, the rebinding wake is skipped, and stale quota escalation resolves its action without scheduling; the self-declared old owner fails its issue status/assignee update before inserting. The old-owner nested-only wake is likewise skipped after restore. |
| Same file: delayed disposition repair eligibility and wake-lock lifetime | Pending execution state is a durable waiting path: the real recovery sweep during the pause schedules no delayed disposition retry. With a receipt-insert pause before a new nested-only run, restore conflicts while wake holds the issue lock; moving that lock outside the transaction instead lets restore return 200 before the run inserts. |
| Same file: direct delayed scheduler after restoration's final read | A stale resolved-action snapshot entering `scheduleDispositionRepairAttempt` after the final read waits on restore's issue lock, then returns `null` with **no receipt or live run**, while restore returns 200; a normal delayed disposition reschedule still queues. Isolated PostgreSQL fixtures only. |

## Writer census and residuals

The restore transaction row-locks existing issue-bound live runs in id order, then the issue, and reads live runs a second time before updating the assignee (the `POST /issues/:id/restore-participant` handler in `server/src/routes/issues.ts`). That second read is not a predicate lock: new writers must retain the issue-row lock through their run or context write. Application writers coordinate on the same issue lock; unknown, malformed or unbound run identities are not a general writer guarantee:

| Writer | Disposition and evidence |
| --- | --- |
| Bounded retry with nested-only issue binding | **Observed stale run, now guarded for all retry reason branches.** `scheduleBoundedRetryForRun` in `heartbeat.ts` locks valid nested `paperclipIssue.id` before predecessor handling and successor insertion, including max-turn and interaction-infrastructure continuation paths. Under that lock, an old agent that is neither assignee nor pending agent participant cannot schedule a retry for that pending stage. Executed failed-bootstrap, max-turn and interaction-infrastructure overlaps formerly produced scheduled successors plus restore 200; now each returns `not_scheduled` with no successor. |
| Same-scope context coalescing | **Observed stale binding, now guarded.** `enqueueWakeup` locks the coalesced run then the nested issue in one transaction through its context update and receipt. It skips an old agent that is neither assignee nor pending participant; the formerly stale queued-run binding is unchanged when restore commits first. |
| Self-declared run | **Observed guarded state, not a continuous lock.** `selfDeclaredRunService` permits `blocked` only for an expired session and atomically changes its status to `in_progress` while requiring the old assignee, then inserts its run separately. In the executed post-final-read overlap, restore won first, the old owner failed the issue update with 403, and no new run was inserted. A self-declared status update that wins first makes restore's status compare-and-set fail. |
| Provider-quota recovery monitor | **Observed stale run, now guarded.** `escalateStrandedAssignedIssue` resolves an action minted from a stale pre-restore snapshot if the pending participant became assignee while it waited for the issue lock; its monitor locks the current issue through insertion and refuses an older agent when the participant now owns the pending stage. The formerly scheduled old-owner retry and active action are both absent after the executed overlap. |
| Delayed disposition repair retry | **Direct insert race reproduced, now guarded.** The R9 assurance harness observed a stale restore 200 in 20/20 direct delayed-insert overlaps despite the sweep's `execution_stage` durable-wait classification. The delayed scheduler now locks the source issue through receipt/run insertion and rechecks assignee and terminal status. In an isolated PostgreSQL post-read restore overlap with a stale resolved-action snapshot, it returns `null`, writes no receipt/run, and restore returns 200. Removing that issue lock **after dropping the database trigger** admits the former owner's scheduled retry alongside restore 200 (R9-A, [executed evidence](pr-evidence/restore-participant-lock-mutant-2026-10-27.md)). The normal sweep still returns `covered` for a pending stage and active actions disqualify restore. |
| Hand-run operator SQL | **Residual race, unguarded.** A `heartbeat_runs` insert issued directly in SQL after restore's final read bypasses issue-row admission and can leave a former-owner run while restore returns 200. At R9, serving-role raw inserts committed during restore's post-read pause in 20/20 overlaps. No database trigger is installed, SQL privileges are not revoked, and no predicate/table lock is taken; this is the named documented residual (alongside unbound runs and unsupported binding formats). Nothing enforces the issue lock for a future application writer that inserts a live run or grants this restore; a typed-lock guard is tracked as a follow-up design. |

These paths do not change the tested happy-path preservation contract. The executed interleavings do not guarantee hand-run operator SQL. Nothing enforces the issue lock for a future application writer; the writers above are the tested set. The following receipt-only writes are a different category:

- `enqueueWakeup` in `heartbeat.ts` records a skipped request (or calls `recordExecutionWait`), not a run; the wait-conditioned branch locks the issue, while the direct skipped-receipt insert does not. A later replay must recheck admission.
- `enqueueWake` in `native-runtime/status-decision-committer.ts` inserts a queued `agent_wakeup_requests` receipt with an issue id, not a `heartbeat_runs` row; any subsequent promotion is a separate writer requiring its own check.
- `recordExecutionWait` in `execution-wait.ts` coalesces or inserts a skipped wait receipt with `runId: null`, under the caller's issue-row lock (see its doc comment); it is not a new live run.

Do not use this endpoint for a card with a live run, pending interaction or active recovery action. The tested application writers serialize with restoration. This evidence does not promise exclusivity against hand-run operator SQL, unbound runs, or unsupported binding formats. Nothing enforces the issue lock for a future application writer, and nothing guards a SQL session. Green CI is not release assurance or approval to run repairs against production cards.
