# Final approval delivery preflight

SUP-19860 (AS-02) moves repository-delivery eligibility ahead of the terminal execution-stage decision. Earlier review/approval stages remain card-scoped: they advance normally and cannot publish `paperclip/approved` until every pre-merge stage is genuinely completed and the last decision is approved (see `doc/execution-semantics.md` for stage `phase`).

## Producer contract

Before committing a terminal approved decision, the issue routes reuse the delivery-owner resolver and decision-head resolver. Repository-backed cards must resolve exactly one owned delivery PR, then positively verify its live OPEN, unmerged, non-draft state, recorded repository/branch identity, and unchanged readable head. A cited foreign PR is not delivery. Issues default to `deliveryRequirement: repository_delivery`; only an authorized board or non-assignee actor may explicitly select `record_only`. That selection skips the final open-PR preflight and the shared repository-delivery check on a Done transition after applicable ladder gates. On the current base, a plain Done PATCH without a ladder can therefore return 200 for `record_only` where `repository_delivery` returns 409. Independent-review, approval, ladder, other done-transition, tier, and authorization guards remain in force.

On `PATCH /api/issues/{id}`, an authorized board actor may select `record_only` even when the board user is the current assignee; no reassignment is required. A board user with viewer-only membership remains read-only, including on their own assigned issue: the 403 retains `error: "Viewer access is read-only"`. An agent cannot select it when it is the current assignee or the assignee the PATCH sets, including in a PATCH that reassigns the card. A record-only selection refused with 403 reports `details.reason: record_only_self_assignee` for an assigned agent, or `record_only_not_authorized` for an earlier authorization refusal (including viewer-only membership, no issue-mutation authority, or the org-chain ancestor escape hatch, which does not permit `deliveryRequirement`). An authorized non-assignee may select it. Classification does not skip independent review, approval, ladder, or tier checks; its Done-transition repository-delivery exception is described above.

A `record_only` card with no repository deliverable closes with the Tier 1 no-repository form (SUP-22570): the close comment line `Closed at Tier 1 (landed, not liveness-probed): no-repository-landing — <why Tier 2 was not probed>. Liveness unverified.`, or the structured `doneTier` field `{ "tier": "tier1", "reason": "…", "landing": { "mode": "noRepositoryLanding" } }`. It is accepted only on `PATCH /api/issues/{id}`, from any identified closer (an agent or a board user), when every check holds: the issue is stored as `record_only` (a request that also changes `deliveryRequirement`, `executionWorkspaceId` or `projectWorkspaceId` is refused); its execution workspace is this issue's own, in this company, of kind `isolated_workspace` / `git_worktree` / `git_worktree`; the recorded worktree path (the execution workspace's `providerRef`, else `cwd`; with `branchName` these are board-only: `PATCH /api/execution-workspaces/{id}` refuses an agent key with 403 when the body sets any of the three, `reconcile-branch` is board-only, there is no create route, and the remaining writers are server-internal) resolves into `<instance>/projects/<companyId>/<projectId>/<repo>/.paperclip/worktrees/` and is a linked worktree of that managed checkout, on a branch naming the issue identifier and no other card identifier; that worktree is clean (no modified, staged or untracked content, no skip-worktree or assume-unchanged entries, no submodules, no unmerged entries, no `index.lock`, no `info/exclude` rule the server did not write: the shared file of the managed checkout may hold only blank lines, `#` comments at column 0 and the server's `/.paperclip-repositories/` line, each compared byte for byte, so a trailing space, CR, indentation or any agent-harness or hand-made rule refuses) and has zero commits ahead of the project's default branch, and every other branch or worktree naming the issue is likewise clean and level. Every other local branch in the managed checkout must belong to a card: unattributed foreign branches refuse; branches registered to another card's workspace are that card's. That is, a branch is accepted only when it names this card (and is compared as above), is one of the project's own branches (below), is the recorded `branchName` of another issue's execution workspace in this company and project (a board-only field), or is a rescue branch of another existing card of this company; any other branch refuses whatever its tip, ahead or at this card's own commit. A rescue branch is one the server keeps when it quarantines a dirty worktree (`paperclip/rescue/<ISSUE-ID>/<UTC timestamp>`): it is attributed by its second path segment, so one naming this card is this card's and is compared with the default branch like any other branch naming the issue (ahead refuses, because the rescued work is undelivered), one naming another issue of this company (looked up by identifier, once per measurement and outside the row lock) is that card's and is skipped, and one naming no issue of this company refuses as belonging to no card. The project's own branches are the project workspace's `defaultRef` (the compare base), its `repoRef` (both board-only) and the repository's own default branch, which the measurement reads from GitHub (`GET /repos/{owner}/{repo}` with the company credential, under the same 15-second timeout as the compares, never from the managed checkout's `origin/HEAD`, which an agent worktree can write): the clone's local branch is the remote's HEAD branch and the heartbeat checks out `repoRef`, so those two branches are not foreign work. A read that fails, is not OK or names no default branch refuses the close with a reason saying the repository's default branch could not be read from GitHub. The measurement outside the transaction reads it, and the write's compare-and-set re-reads `repoRef` with the rest of the project's repository and base. Work placed on a real sibling card's registered branch is attributed to that card, and an agent can park this card's work on `paperclip/rescue/<real sibling id>/x`, where it is then attributed to that sibling (the same class as the registered-sibling-branch residual); a foreign card's work placed on the `repoRef` or the remote default branch is treated as the project's own branch (it is not card evidence either way). Ignored entries are dirt too, except the regenerated-artefact directories named in `IGNORED_ARTIFACT_DIRECTORY_NAMES` (`server/src/services/hardened-git-probe.ts`): `node_modules`, `.pnpm-store`, `dist`, `build`, `.turbo`, `.next`, `coverage`, `__pycache__`, `.venv`, `target`, and the directories Paperclip itself creates in a worktree, `.paperclip` (the worktree provision script), `.paperclip-runtime` (adapter and heartbeat runtime files) and `.paperclip-repositories` (referenced project repositories). A listed name matches at any depth, but only as an ordinary directory with no symlink on the path to it, and only when a committed `.gitignore` rule (or the server's own `info/exclude` line for `.paperclip-repositories`) ignores the directory itself; a symlink named like a listed directory refuses, and so does a listed directory that only an untracked or modified ignore file hides (for example a `target/.gitignore` saying `*`). Ignored files inside the listed regenerated-artefact directories (any depth) are not inspected; any other ignored file refuses, naming the entry. At most five distinct tips (the recorded worktree's and those of branches naming the issue) are compared with GitHub; a sixth refuses the close with `too_many_branch_tips`. That cap bounds the GitHub compares only: the local worktree verification loop is not capped, and what it can cost is an adversarial self-delay of that one close. The repository files the probe reads itself (`info/exclude`, the index and shared indexes) are opened without following symlinks or blocking on a FIFO, and only if they are regular files of bounded size; anything else refuses. The index and every shared index are streamed into the private snapshot, never held in memory, and all of them together may not exceed one 256 MiB budget. "Ahead" is measured on GitHub (the compare API, through the project workspace's repository URL and the company's GitHub credential), never against a ref in the managed checkout, whose refs an agent worktree can write; a tip GitHub cannot compare (for example an unpushed commit), an unreachable GitHub, a missing credential or a missing repository URL refuses the close. The repository and branch it compares against are the project workspace's `repoUrl` and `defaultRef`/`repoRef`, which only a board user can write: `POST /api/companies/{companyId}/projects` (its `workspace` body), `POST /api/projects/{id}/workspaces` and `PATCH /api/projects/{id}/workspaces/{workspaceId}` refuse an agent key (403) before anything is persisted when the body sets any of the three fields (`PUT /api/projects/{id}/repositories` and company import are board-only already, and the repository-attach paths of project creation, `repositoryIds` and `repositoryUrls`, leave `defaultRef` and `repoRef` empty, so the form refuses on them); the issue's `entry-ruling` document (that key exactly) is linked to this issue in this company, states a ruling (it does not open with a placeholder such as `TODO`, `TBD`, `FIXME` or `placeholder`, and has at least three words that are not placeholders), and no revision of it was written by the closer, whether an agent or a board user; the issue has no linked pull request (a pull request mentioned on the issue counts) or `pull_request` work product; and the declaration cites no PR, commit SHA, Git ref or GitHub URL, and names no card identifier other than this card's: in the declaration any `<word>-<number>` token in any case and of any prefix counts (a token such as `OTHER-999`, `other-999`, `SUP-70`, `XSUP-7` or `phase-2` for `SUP-7`; standard names written the same way, such as `ISO-8601`, `SHA-256` or `UTF-8`, do not count). The recorded worktree's branch is checked more narrowly, because the default branch is the identifier followed by the lower-cased issue title (`SUP-7-decide-phase-2-scope`): only upper-case `PREFIX-<n>` tokens and this company's issue prefix in any case count, so a word-number token from the title such as `phase-2`, `sprint-12` or `q3-2026` does not refuse; a lower-case foreign card's branch is refused by the attribution rule above. This card's own issue prefix is never exempt as a standard name (for card `ISO-7`, `ISO-9` and `iso-9` are other cards). The door measures once more just before the status write, outside any transaction: every GitHub compare and the full Git probe run there, never while the issue row is locked. The recorded worktree's status is read last in that measurement, after the GitHub compares, the branch scan and the sibling-worktree verifications: it must still be clean and still on the branch and HEAD measured at the start, or the close refuses. The write transaction then locks the row and compares, without calling GitHub: the issue is still not terminal (a racing close of the same issue that already committed makes every other racer refuse with "the issue's status changed after the close was measured", so one transition writes one verification row and one `issue.updated` row), the stored delivery requirement and workspace binding, and the database half of the proof (workspace, base, ruling identity and revisions, linked pull requests) must all still match the measurement; then it re-checks the one measured worktree with the same hardened Git status (index, status, ignored entries, branch and HEAD; no GitHub compare, no sibling scan) under one shared 15-second budget for the whole re-check (every Git process gets only the time left, and the snapshot copy of the index files counts against it too), so ordinary or ignored dirt written after the measurement refuses; when the budget runs out the close refuses with a distinct reason ("timed out at the close write", not "status could not be verified") and the remedy comment says to retry the close or use the board close path rather than to clean the worktree. Every other refusal at this stage (the measurement before the write or the re-check inside it) leaves one neutral remedy comment: fix what the refusal names, or retry if it says the worktree or the remote could not be verified, keep the issue `record_only` and close again; the board close path stays available. Any mismatch refuses with nothing written. The only window left is between that in-transaction status and the commit of the same transaction. The close audit records what was measured: `issue.done_transition_no_repository_landing_verified`, written in the close transaction, carries the ruling document id and revision, the workspace, repository and base branch, and the probe result (branch, head SHA, compared tips); `issue.done_transition_tier1_close` carries the declaration-time measurement and, as on the base branch, is written once per request before the close transaction, so concurrent closes of one issue each write one even though only the first commits. Other close doors and backstop sweeps refuse the form. `repository_delivery` cards keep their existing forms and checks unchanged, and refuse the no-repository form with a 422 whose `details.remedy` says to have an authorized board user reclassify the card (`PATCH /api/issues/{id}` with `{ "deliveryRequirement": "record_only" }`, which an assignee agent cannot do for its own card) and then close it with the form. This replaces the no-repository form PR 1114 (SUP-23044) landed on the fold branch, which a `repository_delivery` card with no pull request work product or merge commit could also use: a close that records no repository evidence is truthful only where the card is classified as having no repository deliverable and the hardened probe proves the worktree empty, so the `record_only`-only form is the one accepted no-repository close. The PATCH also applies the pending execution-stage transition to the same issue update. If a pending review stage's stored status or assignee has drifted from its current participant, a PATCH that only sets `deliveryRequirement` can restore `status: in_review` and assign that stage's participant (clearing the previous assignee). Inspect the returned status, assignee, and execution state rather than assuming a classification-only mutation.

A refusal returns HTTP 409 with `approval_final_delivery_preflight`, the underlying named reason, `deliveryOwnerIssueId`, and an actionable `remedy`. Draft delivery requires the owner to mark the PR ready and submit the final review again. Missing delivery requires that owner to provide the delivery receipt/PR. The stage stays pending: no approved decision, completion, approval stamp, or merge arm is committed.

A stage approval over a card that owns no open PR is not refused while later stages remain (SUP-24085). Stamp eligibility ignores `post_merge` stages, so on an ADR-072 close ladder (a `pre_merge` review, then `post_merge` stages) the first approve is already stamp-eligible, and before this change a parent card with no PR of its own could not record it. Now, when the decision's resulting state is pending on a later stage that is not completed or skipped and the delivery verdict is `no-pr`, the PATCH verdict, approval comment, and board stage-decision doors record the decision, advance the pointer, and keep the card `in_review`. That decision certifies no head: it is tagged `approvalStatus.finalDeliveryUncertified` with its decision id, and the post-commit hook records `status:skipped:head_uncertified` without resolving, claiming a receipt for, or stamping any head, even when a PR is linked after the preflight. The same tag binds every later stamp writer: `POST /issues/:id/merge-arming/republish` refuses a tagged decision with `head_uncertified`, and the approval-status reconciler skips it with `head_uncertified`, before either resolves a head or touches a receipt. A tag from an earlier decision (its decision id differs from `lastDecisionId`) has no effect. An own PR that is closed unmerged resolves as `no-pr`: a stage approval that does not complete the card is admitted and tagged the same way, and the final approval still refuses. Every other unresolved verdict (draft, unreadable or moved head, ambiguous, not delivered, timeout) still refuses with `approval_final_delivery_preflight`, and a card or binding change during the preflight still refuses with `approval_final_delivery_preflight_stale`, as before. The escalation-accept door runs no preflight before the ladder completes, and the recovery-resolution door is a `done` close that the review-ladder guard refuses while stages remain undecided.

All five terminal approval doors resolve the delivery verdict (bounded by a 20 s timeout) before their write transaction or interaction acceptance; no GitHub request runs under the issue-row lock. Under that lock, each door that holds a repository-delivery prefetch compares the certified issue `status`/`updatedAt`, `assigneeAgentId`, `assigneeUserId` and `executionPolicy` (agent ids in stage participants and `stallEscalation.toAgentId` compare case-insensitively; user ids and assignee columns do not fold, see [execution policy](guides/execution-policy.md)), the `deliveryRequirement` classification, and database delivery binding (repo context, delivery-branch ownership, recorded PR identity, and the certified PR's repo) against the preflight values. A final escalation that starts as `record_only` holds no prefetch, so the locked preflight returns before those comparisons; on that path the route compares only the `deliveryRequirement` classification, and a concurrent assignee or execution-policy change does not reject the approval. A `record_only` PATCH compares only the `deliveryRequirement` classification under the lock, so a concurrent assignee or execution-policy change does not reject it. PATCH and approval-comment auto-close check before persisting the decision; final escalation acceptance checks and then records its decision in the interaction service's transaction, so a stale verdict leaves the interaction pending. For a PATCH that must release its own run first, the route verifies that no other issue field or delivery binding changed during that release, then takes one certificate from the post-release row before entering the transaction. It never re-anchors an existing certificate. Escalation acceptance defers its activity and post-commit actions until the interaction transaction commits. A changed certified card or binding returns HTTP 409 `approval_final_delivery_preflight_stale`; the stage stays pending with no approved decision, receipt publication, or merge arm, and the caller retries.

The agent-id case fold in these compares decides only whether the card changed under the lock. It does not decide who may approve. The actor-versus-seat check and stage membership compare agent and user ids exactly, so an agent whose id matches the seat or a stage participant only by letter case cannot approve; see the boundary in [execution policy](guides/execution-policy.md).

Agent mutation authorization can adopt a stale checkout into the request's live run before PATCH's first certificate. The pre-certificate guard permits only that exact run-link transition when the resulting issue timestamp equals its execution-lock timestamp; unrelated card or delivery changes still refuse. The locked guard compares the resulting certificate to the issue and binding at commit, including any later `updatedAt` change.

An approval comment that interrupts an active run reloads the issue after cancellation releases the run links and may update `updatedAt`. It evaluates the review stage and certifies delivery from that post-interrupt row. A later change during the external preflight still fails the locked recheck.

The check runs on the PATCH verdict, board stage-decision, auto-approval comment, recovery decision, and final escalation-accept routes. Repository-free doc/gate cards retain their existing close semantics. Sanctioned no-deliverable-head overrides remain subject to the existing done guard; they do not bypass ladder or tier requirements. An accepted `doneTransitionOverride` lets an unresolved delivery verdict pass the preflight on the PATCH and recovery-decision routes alike, so an accepted override does not end in `approval_final_delivery_preflight`.

## Done-close draft safety

The done-transition guard includes linked drafts when checking Tier-1 `landing-delegated` declarations and plain (non-approval) closes. Only an open draft whose PR base repository and verified head repository match the card's delivery repository, and whose branch or title identifies the card, receives the named `head_draft` refusal. The HTTP remedy and refusal comment tell the owner to promote it out of draft; a cited, moved, forked, or other-repository PR is not this card's draft delivery. A missing head repository cannot prove draft ownership. Approval-carrying closes keep the preflight's `approval_final_delivery_preflight` / `head_draft` refusal, except that a `head_draft` that rests only on cached open+draft mentions is revalidated live (SUP-24033): if live state shows the card's sole owned mentioned PR merged, the preflight uses the verified merged-carrier path instead, while any live draft that discovery or the mention reads can see still refuses. A draft that discovery cannot see (it sits past the part of the list that was read, or its list entry is malformed) is never assumed absent: in that case the revalidation is not used and the base `head_draft` refusal stands. The revalidation applies only when live discovery read every cached draft's repository completely. Discovery reads page 1 of the open-PR list only (100 entries, no `page` parameter), so a repository counts as read completely only when that response is a short page, has no malformed entry, and has either no `Link` header or a `Link` header that parses fully, has a `rel` in every link-value, has no other parameter, names only `rel="self"`, and whose self target is page 1 of this exact request (same origin, path and query, `page` absent or `1`; a relative, empty, other-host or other-page target does not count). An entry is malformed when it is not an object or when any field that discovery reads is not valid: `number` a positive integer, `head.ref` a string, `title` a string, `draft` a boolean (a non-conforming entry may have been an owned live draft that discovery would drop). Any other `Link` header (`next`, `last`, `prev`, `first`, `previous`, an unknown relation such as one a proxy adds, a link-value with no `rel`, an extra or extended parameter, a self link to another page, host or query, an empty or malformed header) leaves the page unread: a real GitHub page-1 response never carries `prev` or `first` and carries `next` and `last` when more pages exist, so those relations mean more pages or an altered response. A page that is not proven complete means a live draft past it cannot be ruled out, and the `head_draft` refusal stands. A proxy that adds a `Link` relation outside this whitelist therefore costs the revalidation for that repository (the refusal is the base behaviour); a proxy that drops the `Link` header from a list with more pages cannot be detected and is an accepted residual. It also applies only when the card cites at most 5 PRs, and a carrier that passes the live checks still takes the full live merge verification, whose own refusal reason is then returned. On successful live hydration, discovery and ownership use the current branch, title, head repository and draft state instead of stale mention identity; without GitHub credentials, previously refreshed cached evidence remains eligible.

Draft ownership requires a resolved card delivery repository. A linked PR's own base and head repositories matching each other cannot establish ownership when the card's repository is unknown; the backstop leaves that `done` card unchanged.

For older cards already closed `done` over a draft, the hourly done-close landing backstop parks the card `blocked` after its 24-hour grace with a board-owned action to mark the PR ready and republish approval at the ready head. A previously confirmed merged sibling still participates in each later sweep's card-level landing verdict: a remaining draft is audited as superseded, never parked. A missing live head repository cannot establish ownership and leaves the done card unchanged. The park precedes notification; a failed update leaves the done card eligible, and a failed comment leaves the blocked park discoverable even after the seven-day done lookback. The draft-stranded audit marker follows successful comment and assignee wake so an interrupted notification retries. The carrier promotion sweep keeps done parents (not cancelled ones) eligible for its three-day age cap, but only promotes a draft in the parent's delivery repository after two live reads verify its open draft state, head repository and exact branch, and unchanged cached head SHA. A per-company/PR database advisory lock serializes the ledger check, GraphQL ready mutation and durable activity row, so concurrent sweeps produce one promotion record. GitHub's ready mutation accepts no expected-head compare-and-swap: a head change after the final live read remains a remote race. These paths do not publish approval or arm a draft merge.

## Done-close carrier re-check

A Tier-1 `landing-delegated` close re-reads the named carrier PR before the guard accepts it (SUP-24135). The guard sends one read-only GitHub GraphQL query with the token that already serves the auto-merge and merge-queue probes. The query reads the head commit's required checks (`isRequired` for this PR) and `mergeStateStatus`. The guard refuses the close in two cases:

- `carrier_required_check_failed`: a required check run concluded `failure`, `timed_out`, `cancelled` or `startup_failure`, or a required commit status is `failure` or `error`, and no other run of the same check can still pass (a re-run in progress keeps the close allowed). Check runs and commit statuses are separate requirements: a passing status does not hide a failed check run with the same name. The refusal names at most three failed checks, each cut to 80 characters.
- `carrier_merge_conflict`: `mergeStateStatus` is `DIRTY`.

The query reads one page of 100 check contexts. When GitHub reports a next page, or does not report the page boundary, the guard does not refuse on checks: a rerun past context 100 can still pass. A merge conflict still refuses.

`BLOCKED` alone does not refuse: it is the normal state while required checks run or a review is pending. `UNKNOWN` does not refuse: GitHub is still computing it. A merged or closed PR, a failed hydration, or an unreadable probe (non-2xx, GraphQL errors, no token, or no answer within 10 seconds) also does not refuse, because a refusal must rest on live proof. The probe runs only at close time. A carrier that fails after the close stays with the hourly done-close landing backstop and its 24-hour landing verdict.

## Record-only Tier 2 pass contradictions

A `record_only` live close uses `Closed at Tier 2 (live): record-only probe ` followed by a backticked command, `target <observed target> observed <UTC ISO-8601 timestamp> result: pass <pass predicate and observed result>` (or the existing UTC observation range). The structured `doneTier.probeEvidence` carries the same evidence without the close prefix. No merge head is required.

The guard refuses a `result: pass` declaration with `done_transition_record_only_probe_contradiction` when its trailing predicate/result contains one of these eight token-anchored markers (case-insensitive except `REFUSED`, which matches uppercase only):

| Marker name | Recognized form |
| --- | --- |
| `exit_nonzero` | `exit <number>` with a nonzero value |
| `exited_nonzero` | `exited <number>` with a nonzero value |
| `failed_positive` | `failed=<number>` with a positive value |
| `scanned_zero` | `scanned=<number>` whose value is zero |
| `non_clean` | `non-clean` |
| `failed_closed` | `failed closed. All` or `scan failed closed on all 4 repos` (literal probe-failure contexts) |
| `refused` | `REFUSED` |
| `partial_failure` | `partial failure` |

A `<number>` is one complete signed decimal token (integer, fraction such as `.5` or `0.5`, or exponent form such as `1e2`) judged by its numeric value, not by an integer prefix: `scanned=0.5`, `scanned=1e2`, `failed=0.0`, `failed=-1`, `exit 0.0`, and `exit -0` do not contradict a pass, while `scanned=0.0`, `scanned=-0`, `scanned=0e5`, `failed=1.5`, and `exit -0.5` do. Words have word-boundary anchors; phrase separators accept spaces or tabs. Lowercase `refused` (for example `anon request refused 401`) and a bare `failed closed` (for example a predicate confirming an expected negative path) do not contradict a pass; a failed-closed outcome with an explicit failing exit is caught by the `exit`/`exited` markers. This is a bounded marker list, not arbitrary prose inference: it checks only the declaration's predicate/result, not the probe command, target, or unrelated comment text. `exit criteria met`, `exit 0`, `exited 0`, `failed=0`, and `scanned=42` do not contradict a pass. `result: fail` remains refused by the existing failing-predicate rule.

The added `scan failed closed on all 4 repos` context names the failed scan itself even when no exit code or failed count follows it. It does not turn bare `failed closed` into a contradiction marker. A clean declaration with `scanned=4 failed=0 matched=29 armed=0 exit 0` can still close when separate vet lines in the comment report `REFUSED missing paperclip/approved; exit 1`: those lines describe another operation outside the matched declaration predicate.

The refusal names the marker, persists the same specific code (`done_transition_record_only_probe_contradiction`) as `details.code` of its `issue.done_transition_refused` audit row, repeats the accepted form verbatim, and states the honest alternative: **Report the non-clean cycle and do not close.** Re-probe before claiming a genuine pass; do not relabel a failed probe to force a close.

Every accepted Tier 2 record-only close retains the existing machine-readable `issue.done_transition_tier2_close` activity row with `details.tierForm: "record-only"`, probe evidence, observation, and closing-run identity. The row commits atomically with the terminal status, including approval and system-backstop closes. Count that action and `tierForm` to count this class. No contradiction is accepted, so no `issue.done_transition_declared_pass_with_failed_evidence` row is needed.

## Certification and publication

The decision transaction persists `executionState.approvalStatus.approvedHeadSha` and `finalDelivery` (`owner`, `repo`, `number`, `headSha`, `displayName`) from the preflight. Credentials are never persisted in that anchor. The post-commit hook uses this certification instead of certifying a later live head. `finalDelivery` is tagged with the decision id and every decision patch clears any prior-cycle `finalDelivery` first, so the hook only trusts a certification whose `decisionId` equals the card's `lastDecisionId`; a terminal approval that skips the preflight (sanctioned override accepted, repository-free) re-resolves the live head instead. The escalation-accept door mints its decision id inside the shared decision helper, so it re-tags the preflight certification with that id before running the hook. Publication remains delivery-identity-gated and pinned to both the reviewed SHA and repo/PR identity.

The GitHub PR head is externally owned: it is not re-read under the database row lock. If it moves between preflight and publication, the head-pinned publisher returns `status:skipped:head_moved`, writes no status on the new head, and suppresses merge arming. A separate design card covers recertifying the external head at the approval door. If publication instead resolves a different PR than the certified one (same-SHA sibling), it returns `status:skipped:delivery_moved` with the same no-status, no-arm result. The original approved-head anchor survives for the reconciler's existing Guard A content-identity check. Changed content needs fresh review; pending, cancelled, skipped, or incomplete ladders are not approval.

No ruleset, workflow, required context/app pin, override label, allowlist, or merge-authority hard stop changes. AS-03 consumes certified anchors; this change does not manufacture approval for an already-stranded card.
