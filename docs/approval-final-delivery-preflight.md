# Final approval delivery preflight

SUP-19860 (AS-02) moves repository-delivery eligibility ahead of the terminal execution-stage decision. Earlier review/approval stages remain card-scoped: they advance normally and cannot publish `paperclip/approved` until every pre-merge stage is genuinely completed and the last decision is approved (see `doc/execution-semantics.md` for stage `phase`).

## Producer contract

Before committing a terminal approved decision, the issue routes reuse the delivery-owner resolver and decision-head resolver. Repository-backed cards must resolve exactly one owned delivery PR, then positively verify its live OPEN, unmerged, non-draft state, recorded repository/branch identity, and unchanged readable head. A cited foreign PR is not delivery. Issues default to `deliveryRequirement: repository_delivery`; only an authorized board or non-assignee actor may explicitly select `record_only`. That selection skips the final open-PR preflight and the shared repository-delivery check on a Done transition after applicable ladder gates. On the current base, a plain Done PATCH without a ladder can therefore return 200 for `record_only` where `repository_delivery` returns 409. Independent-review, approval, ladder, other done-transition, tier, and authorization guards remain in force.

On `PATCH /api/issues/{id}`, an authorized board actor may select `record_only` even when the board user is the current assignee; no reassignment is required. A board user with viewer-only membership remains read-only, including on their own assigned issue: the 403 retains `error: "Viewer access is read-only"`. An agent cannot select it when it is the current assignee or the assignee the PATCH sets, including in a PATCH that reassigns the card. A record-only selection refused with 403 reports `details.reason: record_only_self_assignee` for an assigned agent, or `record_only_not_authorized` for an earlier authorization refusal (including viewer-only membership, no issue-mutation authority, or the org-chain ancestor escape hatch, which does not permit `deliveryRequirement`). An authorized non-assignee may select it. Classification does not skip independent review, approval, ladder, or tier checks; its Done-transition repository-delivery exception is described above.

A `record_only` card with no repository deliverable closes with the Tier 1 no-repository form (SUP-22570): the close comment line `Closed at Tier 1 (landed, not liveness-probed): no-repository-landing — <why Tier 2 was not probed>. Liveness unverified.`, or the structured `doneTier` field `{ "tier": "tier1", "reason": "…", "landing": { "mode": "noRepositoryLanding" } }`. It is accepted only on `PATCH /api/issues/{id}`, from any identified closer (an agent or a board user), when every check holds: the issue is stored as `record_only` (a request that also changes `deliveryRequirement`, `executionWorkspaceId` or `projectWorkspaceId` is refused); its execution workspace is this issue's own, in this company, of kind `isolated_workspace` / `git_worktree` / `git_worktree`; the recorded worktree path (the execution workspace's `providerRef`, else `cwd`; with `branchName` these are board-only: `PATCH /api/execution-workspaces/{id}` refuses an agent key with 403 when the body sets any of the three, `reconcile-branch` is board-only, there is no create route, and the remaining writers are server-internal) resolves into `<instance>/projects/<companyId>/<projectId>/<repo>/.paperclip/worktrees/` and is a linked worktree of that managed checkout, on a branch naming the issue identifier and no other card identifier; that worktree is clean (no modified, staged or untracked content, no skip-worktree or assume-unchanged entries, no submodules, no unmerged entries, no `index.lock`, no `info/exclude` rule the server did not write) and has zero commits ahead of the project's default branch, and every other branch or worktree naming the issue is likewise clean and level. Every other local branch in the managed checkout must belong to a card: unattributed foreign branches refuse; branches registered to another card's workspace are that card's. That is, a branch is accepted only when it names this card (and is compared as above), is the project's default branch, or is the recorded `branchName` of another issue's execution workspace in this company and project (a board-only field); any other branch refuses whatever its tip, ahead or at this card's own commit. Work placed on a real sibling card's registered branch is attributed to that card. Ignored entries are dirt too, except the regenerated-artefact directories named in `IGNORED_ARTIFACT_DIRECTORY_NAMES` (`server/src/services/hardened-git-probe.ts`): `node_modules`, `.pnpm-store`, `dist`, `build`, `.turbo`, `.next`, `coverage`, `__pycache__`, `.venv`, `target`, and the directories Paperclip itself creates in a worktree, `.paperclip` (the worktree provision script), `.paperclip-runtime` (adapter and heartbeat runtime files) and `.paperclip-repositories` (referenced project repositories). A listed name matches at any depth, but only as an ordinary directory with no symlink on the path to it, and only when a committed `.gitignore` rule (or the server's own `info/exclude` line for `.paperclip-repositories`) ignores the directory itself; a symlink named like a listed directory refuses, and so does a listed directory that only an untracked or modified ignore file hides (for example a `target/.gitignore` saying `*`). Ignored files inside the listed regenerated-artefact directories (any depth) are not inspected; any other ignored file refuses, naming the entry. At most five distinct tips (the recorded worktree's and those of branches naming the issue) are compared with GitHub; a sixth refuses the close with `too_many_branch_tips`. That cap bounds the GitHub compares only: the local worktree verification loop is not capped, and what it can cost is an adversarial self-delay of that one close. The repository files the probe reads itself (`info/exclude`, the index and shared indexes) are opened without following symlinks or blocking on a FIFO, and only if they are regular files of bounded size; anything else refuses. The index and every shared index are streamed into the private snapshot, never held in memory, and all of them together may not exceed one 256 MiB budget. "Ahead" is measured on GitHub (the compare API, through the project workspace's repository URL and the company's GitHub credential), never against a ref in the managed checkout, whose refs an agent worktree can write; a tip GitHub cannot compare (for example an unpushed commit), an unreachable GitHub, a missing credential or a missing repository URL refuses the close. The repository and branch it compares against are the project workspace's `repoUrl` and `defaultRef`/`repoRef`, which only a board user can write: `POST /api/companies/{companyId}/projects` (its `workspace` body), `POST /api/projects/{id}/workspaces` and `PATCH /api/projects/{id}/workspaces/{workspaceId}` refuse an agent key (403) before anything is persisted when the body sets any of the three fields (`PUT /api/projects/{id}/repositories` and company import are board-only already, and the repository-attach paths of project creation, `repositoryIds` and `repositoryUrls`, leave `defaultRef` and `repoRef` empty, so the form refuses on them); the issue's `entry-ruling` document (that key exactly) is linked to this issue in this company, states a ruling (it does not open with a placeholder such as `TODO`, `TBD`, `FIXME` or `placeholder`, and has at least three words that are not placeholders), and no revision of it was written by the closer, whether an agent or a board user; the issue has no linked pull request (a pull request mentioned on the issue counts) or `pull_request` work product; and the declaration cites no PR, commit SHA, Git ref or GitHub URL, and names no card identifier other than this card's, in any case (a token such as `OTHER-999`, `other-999`, `SUP-70` or `XSUP-7` for `SUP-7`; standard names written the same way, such as `ISO-8601`, `SHA-256` or `UTF-8`, do not count, while any other word-number token such as `phase-2` does, so a declaration or branch carrying one refuses). The door measures once more just before the status write, outside any transaction: every GitHub compare and the full Git probe run there, never while the issue row is locked. The recorded worktree's status is read last in that measurement, after the GitHub compares, the branch scan and the sibling-worktree verifications: it must still be clean and still on the branch and HEAD measured at the start, or the close refuses. The write transaction then locks the row and compares, without calling GitHub: the issue is still not terminal (a racing close of the same issue that already committed makes every other racer refuse with "the issue's status changed after the close was measured", so one transition writes one verification row and one `issue.updated` row), the stored delivery requirement and workspace binding, and the database half of the proof (workspace, base, ruling identity and revisions, linked pull requests) must all still match the measurement; then it re-checks the one measured worktree with the same hardened Git status (index, status, ignored entries, branch and HEAD; no GitHub compare, no sibling scan) under a 5-second timeout, so ordinary or ignored dirt written after the measurement refuses. Any mismatch refuses with nothing written. The only window left is between that in-transaction status and the commit of the same transaction. The close audit records what was measured: `issue.done_transition_no_repository_landing_verified`, written in the close transaction, carries the ruling document id and revision, the workspace, repository and base branch, and the probe result (branch, head SHA, compared tips); `issue.done_transition_tier1_close` carries the declaration-time measurement and, as on the base branch, is written once per request before the close transaction, so concurrent closes of one issue each write one even though only the first commits. Other close doors and backstop sweeps refuse the form. `repository_delivery` cards keep their existing forms and checks unchanged, and refuse the no-repository form with a 422 whose `details.remedy` says to have an authorized board user reclassify the card (`PATCH /api/issues/{id}` with `{ "deliveryRequirement": "record_only" }`, which an assignee agent cannot do for its own card) and then close it with the form. This replaces the no-repository form PR 1114 (SUP-23044) landed on the fold branch, which a `repository_delivery` card with no pull request work product or merge commit could also use: a close that records no repository evidence is truthful only where the card is classified as having no repository deliverable and the hardened probe proves the worktree empty, so the `record_only`-only form is the one accepted no-repository close. The record_only worktree probe runs a root-owned git from a fixed system path with no inherited `GIT_*` environment and no system or global config, forces `core.fsmonitor` and `core.hooksPath` off, allows no transport and no lazy fetch (`GIT_ALLOW_PROTOCOL` empty, `GIT_NO_LAZY_FETCH`) and applies a timeout that kills the git process's whole process group, and reads worktree status through a private snapshot git dir, so repository-local configuration (fsmonitor, hooks, filter drivers, `include`/`includeIf` targets, promisor remotes with `core.sshCommand` or `uploadpack` helpers) cannot execute and does not make the form unavailable; a `core.worktree` redirect in per-worktree config (`extensions.worktreeConfig`) is refused ("not a Git work tree"), while in the shared repository config Git ignores `core.worktree` for linked worktrees, so the real worktree is measured and a dirty one is refused (422). Every unmeasured step (no root-owned git, a timeout, a snapshot or temporary-directory failure) refuses the close. The pre-existing repository-delivery status probe (`git status --porcelain`) and the issue-attribution commit count keep their behavior and fail-open contract, and run with the server's own git environment and configuration (so `safe.directory` entries in `GIT_CONFIG_*` or in global and system config still apply), minus `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`, with fsmonitor and hooks forced off on the command line and, as before, no timeout (a slow status finishes and blocks rather than timing out into a fail-open); on a host with no root-owned git they fall back to the `git` on `PATH`. The record_only probe keeps its 15-second timeout and refuses the close when it fires.

The PATCH also applies the pending execution-stage transition to the same issue update. If a pending review stage's stored status or assignee has drifted from its current participant, a PATCH that only sets `deliveryRequirement` can restore `status: in_review` and assign that stage's participant (clearing the previous assignee). Inspect the returned status, assignee, and execution state rather than assuming a classification-only mutation.

A refusal returns HTTP 409 with `approval_final_delivery_preflight`, the underlying named reason, `deliveryOwnerIssueId`, and an actionable `remedy`. Draft delivery requires the owner to mark the PR ready and submit the final review again. Missing delivery requires that owner to provide the delivery receipt/PR. The stage stays pending: no approved decision, completion, approval stamp, or merge arm is committed.

All five terminal approval doors resolve the delivery verdict (bounded by a 20 s timeout) before their write transaction or interaction acceptance; no GitHub request runs under the issue-row lock. Under that lock, each door that holds a repository-delivery prefetch compares the certified issue `status`/`updatedAt`, `assigneeAgentId`, `assigneeUserId` and `executionPolicy`, the `deliveryRequirement` classification, and database delivery binding (repo context, delivery-branch ownership, recorded PR identity, and the certified PR's repo) against the preflight values. A final escalation that starts as `record_only` holds no prefetch, so the locked preflight returns before those comparisons; on that path the route compares only the `deliveryRequirement` classification, and a concurrent assignee or execution-policy change does not reject the approval. A `record_only` PATCH compares only the `deliveryRequirement` classification under the lock, so a concurrent assignee or execution-policy change does not reject it. PATCH and approval-comment auto-close check before persisting the decision; final escalation acceptance checks and then records its decision in the interaction service's transaction, so a stale verdict leaves the interaction pending. For a PATCH that must release its own run first, the route verifies that no other issue field or delivery binding changed during that release, then takes one certificate from the post-release row before entering the transaction. It never re-anchors an existing certificate. Escalation acceptance defers its activity and post-commit actions until the interaction transaction commits. A changed certified card or binding returns HTTP 409 `approval_final_delivery_preflight_stale`; the stage stays pending with no approved decision, receipt publication, or merge arm, and the caller retries.

Agent mutation authorization can adopt a stale checkout into the request's live run before PATCH's first certificate. The pre-certificate guard permits only that exact run-link transition when the resulting issue timestamp equals its execution-lock timestamp; unrelated card or delivery changes still refuse. The locked guard compares the resulting certificate to the issue and binding at commit, including any later `updatedAt` change.

An approval comment that interrupts an active run reloads the issue after cancellation releases the run links and may update `updatedAt`. It evaluates the review stage and certifies delivery from that post-interrupt row. A later change during the external preflight still fails the locked recheck.

The check runs on the PATCH verdict, board stage-decision, auto-approval comment, recovery decision, and final escalation-accept routes. Repository-free doc/gate cards retain their existing close semantics. Sanctioned no-deliverable-head overrides remain subject to the existing done guard; they do not bypass ladder or tier requirements. An accepted `doneTransitionOverride` lets an unresolved delivery verdict pass the preflight on the PATCH and recovery-decision routes alike, so an accepted override does not end in `approval_final_delivery_preflight`.

## Done-close draft safety

The done-transition guard includes linked drafts when checking Tier-1 `landing-delegated` declarations and plain (non-approval) closes. Only an open draft whose PR base repository and verified head repository match the card's delivery repository, and whose branch or title identifies the card, receives the named `head_draft` refusal. The HTTP remedy and refusal comment tell the owner to promote it out of draft; a cited, moved, forked, or other-repository PR is not this card's draft delivery. A missing head repository cannot prove draft ownership. Approval-carrying closes keep the preflight's `approval_final_delivery_preflight` / `head_draft` refusal. On successful live hydration, discovery and ownership use the current branch, title, head repository and draft state instead of stale mention identity; without GitHub credentials, previously refreshed cached evidence remains eligible.

Draft ownership requires a resolved card delivery repository. A linked PR's own base and head repositories matching each other cannot establish ownership when the card's repository is unknown; the backstop leaves that `done` card unchanged.

For older cards already closed `done` over a draft, the hourly done-close landing backstop parks the card `blocked` after its 24-hour grace with a board-owned action to mark the PR ready and republish approval at the ready head. A previously confirmed merged sibling still participates in each later sweep's card-level landing verdict: a remaining draft is audited as superseded, never parked. A missing live head repository cannot establish ownership and leaves the done card unchanged. The park precedes notification; a failed update leaves the done card eligible, and a failed comment leaves the blocked park discoverable even after the seven-day done lookback. The draft-stranded audit marker follows successful comment and assignee wake so an interrupted notification retries. The carrier promotion sweep keeps done parents (not cancelled ones) eligible for its three-day age cap, but only promotes a draft in the parent's delivery repository after two live reads verify its open draft state, head repository and exact branch, and unchanged cached head SHA. A per-company/PR database advisory lock serializes the ledger check, GraphQL ready mutation and durable activity row, so concurrent sweeps produce one promotion record. GitHub's ready mutation accepts no expected-head compare-and-swap: a head change after the final live read remains a remote race. These paths do not publish approval or arm a draft merge.

## Certification and publication

The decision transaction persists `executionState.approvalStatus.approvedHeadSha` and `finalDelivery` (`owner`, `repo`, `number`, `headSha`, `displayName`) from the preflight. Credentials are never persisted in that anchor. The post-commit hook uses this certification instead of certifying a later live head. `finalDelivery` is tagged with the decision id and every decision patch clears any prior-cycle `finalDelivery` first, so the hook only trusts a certification whose `decisionId` equals the card's `lastDecisionId`; a terminal approval that skips the preflight (sanctioned override accepted, repository-free) re-resolves the live head instead. The escalation-accept door mints its decision id inside the shared decision helper, so it re-tags the preflight certification with that id before running the hook. Publication remains delivery-identity-gated and pinned to both the reviewed SHA and repo/PR identity.

The GitHub PR head is externally owned: it is not re-read under the database row lock. If it moves between preflight and publication, the head-pinned publisher returns `status:skipped:head_moved`, writes no status on the new head, and suppresses merge arming. A separate design card covers recertifying the external head at the approval door. If publication instead resolves a different PR than the certified one (same-SHA sibling), it returns `status:skipped:delivery_moved` with the same no-status, no-arm result. The original approved-head anchor survives for the reconciler's existing Guard A content-identity check. Changed content needs fresh review; pending, cancelled, skipped, or incomplete ladders are not approval.

No ruleset, workflow, required context/app pin, override label, allowlist, or merge-authority hard stop changes. AS-03 consumes certified anchors; this change does not manufacture approval for an already-stranded card.

## Verification

The route suite also checks a successful no-recovery close after the assignee's stale checkout is adopted, and an outside timestamp mutation after that adoption but before approval persists.

The execution-decisions route suite covers final draft and missing-delivery refusals, successful independent final approval including own active-run cancellation, a post-preflight content push, mid-ladder advancement, repository-free close, and deterministic status/`updatedAt`, recorded PR identity, stage-transition and delivery-binding races before each of the three terminal decision transactions. Assignee and execution-policy races are pinned on the PATCH door only: one held-preflight case per field changes the field between preflight and the decision transaction. A separate PATCH held-preflight case on a `record_only` card pins the skip: an assignee or execution-policy change after preflight does not return the stale rejection. Final escalation acceptance also pins classification flips in both directions, alone and combined with an execution-policy change. A separate held-preflight case catches a timestamp change before PATCH certification. The race assertions check HTTP 409, pending stage, no decision or accepted interaction, unchanged delivery receipt, no approval publication, and no merge-arm request. Run the scoped suite directly:

```sh
pnpm --filter @paperclipai/server exec vitest run src/__tests__/issue-execution-decisions-routes.test.ts
pnpm typecheck
```

The root stable runner currently rejects the card's positional `pnpm test:run -- <file>` spelling; it is not an alias for Vitest's filename filter. Sandbox verification should inspect actual HTTP responses, persisted execution state/decision rows, and outbound status transport, not mock-returned expected execution state. Production/live exercise remains owner-gated.

The existing refusal suites also assert that a preflight 409 leaves the issue and decision rows unchanged, creates no comment, and sends no approval status. An ambiguity refusal replaces approval-time `pendingCandidates`/`skipReason` with candidate identities and the named owner/remedy in the refusal details. There is no successor certification timestamp: `approvalStatus` stays absent and `lastDecisionId`/`lastDecisionOutcome` stay null. The board-race regression requires one first-stage winner, no losing-request effects before retry, one decision/comment/audit per stage, and final state and wake targets equal to a sequential two-stage control. Existing system diagnostics are counted separately so duplicate comments cannot hide behind the retry.
