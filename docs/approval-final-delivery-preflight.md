# Final approval delivery preflight

SUP-19860 (AS-02) moves repository-delivery eligibility ahead of the terminal execution-stage decision. Earlier review/approval stages remain card-scoped: they advance normally and cannot publish `paperclip/approved` until every pre-merge stage is genuinely completed and the last decision is approved (see `doc/execution-semantics.md` for stage `phase`).

## Producer contract

Before committing a terminal approved decision, the issue routes reuse the delivery-owner resolver and decision-head resolver. Repository-backed cards must resolve exactly one owned delivery PR, then positively verify its live OPEN, unmerged, non-draft state, recorded repository/branch identity, and unchanged readable head. A cited foreign PR is not delivery. Issues default to `deliveryRequirement: repository_delivery`; only an authorized board or non-assignee actor may explicitly select `record_only`. That selection skips the final open-PR preflight and the shared repository-delivery check on a Done transition after applicable ladder gates. On the current base, a plain Done PATCH without a ladder can therefore return 200 for `record_only` where `repository_delivery` returns 409. Independent-review, approval, ladder, other done-transition, tier, and authorization guards remain in force.

On `PATCH /api/issues/{id}`, an authorized board actor may select `record_only` even when the board user is the current assignee; no reassignment is required. A board user with viewer-only membership remains read-only, including on their own assigned issue: the 403 retains `error: "Viewer access is read-only"`. An agent cannot select it when it is the current assignee or the assignee the PATCH sets, including in a PATCH that reassigns the card. A record-only selection refused with 403 reports `details.reason: record_only_self_assignee` for an assigned agent, or `record_only_not_authorized` for an earlier authorization refusal (including viewer-only membership, no issue-mutation authority, or the org-chain ancestor escape hatch, which does not permit `deliveryRequirement`). An authorized non-assignee may select it. Classification does not skip independent review, approval, ladder, or tier checks; its Done-transition repository-delivery exception is described above. One tier exception follows from it (SUP-23347): when a review participant's recorded decision carries the close (a `PATCH` done with an approved review decision, or a `## Review: APPROVED` comment) and the delivery guard skipped with `record_only_delivery_skipped`, a close comment with no done-tier declaration text at all is accepted as an audited skip (`issue.done_tier_declaration_skipped` with `skipReason: record_only_review_decision`). A malformed or refused tier line, a close with no comment, and a board close without a participant decision still refuse.

A `record_only` card with no repository deliverable closes with the Tier 1 no-repository form (SUP-22570): the close comment line `Closed at Tier 1 (landed, not liveness-probed): no-repository-landing — <why Tier 2 was not probed>. Liveness unverified.`, or the structured `doneTier` field `{ "tier": "tier1", "reason": "…", "landing": { "mode": "noRepositoryLanding" } }`. It is accepted only on `PATCH /api/issues/{id}`, from any identified closer (an agent or a board user), when every check holds: the issue is stored as `record_only` (a request that also changes `deliveryRequirement`, `executionWorkspaceId` or `projectWorkspaceId` is refused); its execution workspace is this issue's own, in this company, of kind `isolated_workspace` / `git_worktree` / `git_worktree`; the recorded worktree path (the execution workspace's `providerRef`, else `cwd`; with `branchName` these are board-only: `PATCH /api/execution-workspaces/{id}` refuses an agent key with 403 when the body sets any of the four (the three or `baseRef`), `reconcile-branch` is board-only, there is no create route, and the remaining writers are server-internal) resolves into `<instance>/projects/<companyId>/<projectId>/<repo>/.paperclip/worktrees/` and is a linked worktree of that managed checkout, on a branch naming the issue identifier and no other card identifier; that worktree is clean (no modified, staged or untracked content, no skip-worktree or assume-unchanged entries, no submodules, no unmerged entries, no `index.lock`, no `info/exclude` rule the server did not write: the shared file of the managed checkout may hold only blank lines, `#` comments at column 0 and the server's `/.paperclip-repositories/` line, each compared byte for byte, so a trailing space, CR, indentation or any agent-harness or hand-made rule refuses) and has zero commits ahead of the project's default branch, and every other branch or worktree naming the issue is likewise clean and level. Every other local branch in the managed checkout must belong to a card: unattributed foreign branches refuse; branches registered to another card's workspace are that card's. That is, a branch is accepted only when it names this card (and is compared as above), is one of the project's own branches (below), is the recorded `branchName` of another issue's execution workspace in this company and project (a board-only field), or is a rescue branch of another existing card of this company; any other branch refuses whatever its tip, ahead or at this card's own commit. A rescue branch is one the server keeps when it quarantines a dirty worktree (`paperclip/rescue/<ISSUE-ID>/<UTC timestamp>`): it is attributed by its second path segment, so one naming this card is this card's and is compared with the default branch like any other branch naming the issue (ahead refuses, because the rescued work is undelivered), one naming another issue of this company (looked up by identifier, once per measurement and outside the row lock) is that card's and is skipped, and one naming no issue of this company refuses as belonging to no card. The project's own branches are the project workspace's `defaultRef` (the compare base), its `repoRef` (both board-only) and the repository's own default branch, which the measurement reads from GitHub (`GET /repos/{owner}/{repo}` with the company credential, under the same 15-second timeout as the compares, never from the managed checkout's `origin/HEAD`, which an agent worktree can write): the clone's local branch is the remote's HEAD branch and the heartbeat checks out `repoRef`, so those two branches are not foreign work. A read that fails, is not OK or names no default branch refuses the close with a reason saying the repository's default branch could not be read from GitHub. The measurement outside the transaction reads it, and the write's compare-and-set re-reads `repoRef` with the rest of the project's repository and base. Work placed on a real sibling card's registered branch is attributed to that card, and an agent can park this card's work on `paperclip/rescue/<real sibling id>/x`, where it is then attributed to that sibling (the same class as the registered-sibling-branch residual); a foreign card's work placed on the `repoRef` or the remote default branch is treated as the project's own branch (it is not card evidence either way). Ignored entries are dirt too, except the regenerated-artefact directories named in `IGNORED_ARTIFACT_DIRECTORY_NAMES` (`server/src/services/hardened-git-probe.ts`): `node_modules`, `.pnpm-store`, `dist`, `build`, `.turbo`, `.next`, `coverage`, `__pycache__`, `.venv`, `target`, and the directories Paperclip itself creates in a worktree, `.paperclip` (the worktree provision script), `.paperclip-runtime` (adapter and heartbeat runtime files) and `.paperclip-repositories` (referenced project repositories). A listed name matches at any depth, but only as an ordinary directory with no symlink on the path to it, and only when a committed `.gitignore` rule (or the server's own `info/exclude` line for `.paperclip-repositories`) ignores the directory itself; a symlink named like a listed directory refuses, and so does a listed directory that only an untracked or modified ignore file hides (for example a `target/.gitignore` saying `*`). Ignored files inside the listed regenerated-artefact directories (any depth) are not inspected; any other ignored file refuses, naming the entry. At most five distinct tips (the recorded worktree's and those of branches naming the issue) are compared with GitHub; a sixth refuses the close with `too_many_branch_tips`. That cap bounds the GitHub compares only: the local worktree verification loop is not capped, and what it can cost is an adversarial self-delay of that one close. The repository files the probe reads itself (`info/exclude`, the index and shared indexes) are opened without following symlinks or blocking on a FIFO, and only if they are regular files of bounded size; anything else refuses. The index and every shared index are streamed into the private snapshot, never held in memory, and all of them together may not exceed one 256 MiB budget. "Ahead" is measured on GitHub (the compare API, through the project workspace's repository URL and the company's GitHub credential), never against a ref in the managed checkout, whose refs an agent worktree can write; a tip GitHub cannot compare (for example an unpushed commit), an unreachable GitHub, a missing credential or a missing repository URL refuses the close. The repository and branch it compares against are the project workspace's `repoUrl` and `defaultRef`/`repoRef`, which only a board user can write: `POST /api/companies/{companyId}/projects` (its `workspace` body), `POST /api/projects/{id}/workspaces` and `PATCH /api/projects/{id}/workspaces/{workspaceId}` refuse an agent key (403) before anything is persisted when the body sets any of the three fields (`PUT /api/projects/{id}/repositories` and company import are board-only already, and the repository-attach paths of project creation, `repositoryIds` and `repositoryUrls`, leave `defaultRef` and `repoRef` empty, so the form refuses on them); the issue's `entry-ruling` document (that key exactly) is linked to this issue in this company, states a ruling (it does not open with a placeholder such as `TODO`, `TBD`, `FIXME` or `placeholder`, and has at least three words that are not placeholders), and no revision of it was written by the closer, whether an agent or a board user; the issue has no linked pull request (a pull request mentioned on the issue counts) or `pull_request` work product; and the declaration cites no PR, commit SHA, Git ref or GitHub URL, and names no card identifier other than this card's: in the declaration any `<word>-<number>` token in any case and of any prefix counts (a token such as `OTHER-999`, `other-999`, `SUP-70`, `XSUP-7` or `phase-2` for `SUP-7`; standard names written the same way, such as `ISO-8601`, `SHA-256` or `UTF-8`, do not count). The recorded worktree's branch is checked more narrowly, because the default branch is the identifier followed by the lower-cased issue title (`SUP-7-decide-phase-2-scope`): only upper-case `PREFIX-<n>` tokens and this company's issue prefix in any case count, so a word-number token from the title such as `phase-2`, `sprint-12` or `q3-2026` does not refuse; a lower-case foreign card's branch is refused by the attribution rule above. This card's own issue prefix is never exempt as a standard name (for card `ISO-7`, `ISO-9` and `iso-9` are other cards). The door measures once more just before the status write, outside any transaction: every GitHub compare and the full Git probe run there, never while the issue row is locked. The recorded worktree's status is read last in that measurement, after the GitHub compares, the branch scan and the sibling-worktree verifications: it must still be clean and still on the branch and HEAD measured at the start, or the close refuses. The write transaction then locks the row and compares, without calling GitHub: the issue is still not terminal (a racing close of the same issue that already committed makes every other racer refuse with "the issue's status changed after the close was measured", so one transition writes one verification row and one `issue.updated` row), the stored delivery requirement and workspace binding, and the database half of the proof (workspace, base, ruling identity and revisions, linked pull requests) must all still match the measurement; then it re-checks the one measured worktree with the same hardened Git status (index, status, ignored entries, branch and HEAD; no GitHub compare, no sibling scan) under one shared 15-second budget for the whole re-check (every Git process gets only the time left, and the snapshot copy of the index files counts against it too), so ordinary or ignored dirt written after the measurement refuses; when the budget runs out the close refuses with a distinct reason ("timed out at the close write", not "status could not be verified") and the remedy comment says to retry the close or use the board close path rather than to clean the worktree. Every other refusal at this stage (the measurement before the write or the re-check inside it) leaves one neutral remedy comment: fix what the refusal names, or retry if it says the worktree or the remote could not be verified, keep the issue `record_only` and close again; the board close path stays available. Any mismatch refuses with nothing written. The only window left is between that in-transaction status and the commit of the same transaction. The close audit records what was measured: `issue.done_transition_no_repository_landing_verified`, written in the close transaction, carries the ruling document id and revision, the workspace, repository and base branch, and the probe result (branch, head SHA, compared tips); `issue.done_transition_tier1_close` carries the declaration-time measurement and, as on the base branch, is written once per request before the close transaction, so concurrent closes of one issue each write one even though only the first commits. Other close doors and backstop sweeps refuse the form. `repository_delivery` cards keep their existing forms and checks unchanged, except one added Tier 2 close (SUP-24402): a card with no pull request, no recorded merge commit and no `record_only` classification closes at Tier 2 only when the server itself proves its own recorded worktree — resolved into the managed worktree layout and a linked worktree of the managed checkout — has zero commits ahead of the base ref, a HEAD that is an ancestor of the base ref (in the worktree and on the remote), no tracked changes, no untracked files, no ignored entries outside the regenerated-artefact directories, no stash, no other branch naming this issue with commits ahead of the base, and no other worktree on a branch naming this issue (or with a detached HEAD) holding uncommitted work, the measured worktree is re-checked inside the close write, and the declaration's probe head names that HEAD (see `proveZeroDeltaRepositoryClose` in `server/src/services/done-transition-guard.ts`); the workspace `baseRef` it is measured against is board-only like the worktree path and branch (`PATCH /api/execution-workspaces/{id}` refuses an agent key with 403 when the body sets `baseRef`); `record_only` handling is unchanged. They refuse the no-repository form with a 422 whose `details.remedy` says to have an authorized board user reclassify the card (`PATCH /api/issues/{id}` with `{ "deliveryRequirement": "record_only" }`, which an assignee agent cannot do for its own card) and then close it with the form. This replaces the no-repository form PR 1114 (SUP-23044) landed on the fold branch, which a `repository_delivery` card with no pull request work product or merge commit could also use: a close that records no repository evidence is truthful only where the card is classified as having no repository deliverable and the hardened probe proves the worktree empty, so the `record_only`-only form is the one accepted no-repository close. The record_only worktree probe runs a root-owned git from a fixed system path with no inherited `GIT_*` environment and no system or global config, forces `core.fsmonitor` and `core.hooksPath` off, allows no transport and no lazy fetch (`GIT_ALLOW_PROTOCOL` empty, `GIT_NO_LAZY_FETCH`) and applies a timeout that kills the git process's whole process group, and reads worktree status through a private snapshot git dir, so repository-local configuration (fsmonitor, hooks, filter drivers, `include`/`includeIf` targets, promisor remotes with `core.sshCommand` or `uploadpack` helpers) cannot execute and does not make the form unavailable; a `core.worktree` redirect in per-worktree config (`extensions.worktreeConfig`) is refused ("not a Git work tree"), while in the shared repository config Git ignores `core.worktree` for linked worktrees, so the real worktree is measured and a dirty one is refused (422). Every unmeasured step (no root-owned git, a timeout, a snapshot or temporary-directory failure) refuses the close. The pre-existing repository-delivery status probe (`git status --porcelain`) and the issue-attribution commit count keep their behavior and fail-open contract, and run with the server's own git environment and configuration (so `safe.directory` entries in `GIT_CONFIG_*` or in global and system config still apply), minus `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`, with fsmonitor and hooks forced off on the command line and, as before, no timeout (a slow status finishes and blocks rather than timing out into a fail-open); on a host with no root-owned git they fall back to the `git` on `PATH`. The record_only probe keeps its 15-second timeout and refuses the close when it fires.

The record-only probe and its close-write recheck read the shared stash for this card only (the provenance rule). Every stash commit records, in its own subject, the branch it was made on (`WIP on <branch>: …` or `On <branch>: …`). A stash recorded on this card's recorded branch, or on any branch that carries this card's identifier and is not registered to another card, refuses the close. This includes an entry below the top of the stack, a packed stash ref, a stash ref with no reflog line, and a stash whose list label was rewritten with `git stash store -m`: the list label is never read, so relabelling changes no decision in either direction. Parents are not read either, because a record-only card's own stash shares its first parent with every other card's stash on the same base commit. Every other stash has no effect on this card: another card's, one on a project branch, one on an unregistered or deleted branch that does not carry this card's identifier, a detached-HEAD stash, and stash evidence that cannot be read (a garbage ref, a non-commit, a missing or corrupt object, a missing reflog). The stash reflog file (`<common dir>/logs/refs/stash`) is read up to a 16 MiB bound: a regular reflog file over that bound, or one that cannot be read whole, refuses the close as unverified, because long `git stash push -m` messages can grow it past the bound and dropping it would hide this card's entries below the top; anything other than a regular file in its place also refuses as unverified: a symbolic link or a FIFO, which git reads the stash stack through while the probe neither follows links nor reads FIFOs, and a socket, a device or a directory, including one swapped in between the probe's first check and its read; only a missing reflog has no effect. Closing never drops or rewrites a stash. These local names are advisory attribution, not delivery proof. Residual blind spot: a stash this card makes on a detached HEAD, on a temporary branch that does not carry its identifier and is then deleted, or while switched onto another card's branch, and a stash commit rebuilt with `git commit-tree` under another subject, record a branch that is not this card's and do not refuse; a detached-HEAD stash of this card cannot be told apart from another card's. Zero-delta repository-delivery closes keep their repository-wide stash refusal: any stash, and any unreadable stash evidence, refuses.

The zero-delta `repository_delivery` Tier 2 close (SUP-24402) is accepted only on `PATCH /api/issues/{id}`, the one door that re-checks its measurement inside the status write; the comment auto-approval, recovery, review-escalation and create doors and the backstop sweep refuse it with the `merge_commit_unrecorded` refusal. A PATCH that also changes the card's `projectId`, `projectWorkspaceId` or `executionWorkspaceId` refuses. The admitting fact is the forge snapshot of the board-recorded repository: every branch and tag tip is on the base line or is a pull-request head, a ref whose name carries this card is on the base line, and the declared head is on the base line. A branch or unmerged pull-request head whose name mentions this card but is registered by the board, by exact name, to another card's workspace is that card's: it must still be on the base line or be a pull-request head like any other branch, but it does not have to land for this card to close. This card's own recorded branch, tags and other ref namespaces are never exempted this way. A branch or tag name is never a reason to skip that tip. The close write re-reads that snapshot under a 20-second budget while the issue row is held and refuses if the digest changed. Local checks, including a remote-tracking ref, a packed ref, a reflog tip, and a broken loose ref, can only refuse. A proven zero-delta measurement is the stated path through the final-stage approval preflight when the only unresolved verdict is `no-pr`, and that decision is tagged `finalDeliveryUncertified` with a `zero-delta:` reason. The final-stage participant sends one PATCH carrying both the approval and the Tier 2 declaration.

Pull-request accounting accepts only heads whose `head.repo.full_name` matches the board-recorded repository. Fork heads and heads without a readable repository identity do not account for a tip. The snapshot digest covers that exact head set, all non-pull forge refs, and unmerged PR head names and SHAs. Both reads use the same snapshot budget and bracket the complete ref inventory and all PR pages with the base read. A moved, removed, or newly foreign PR head therefore refuses the close even if no branch or tag moved. Card-named refs and the card's recorded branch still receive an ancestry comparison when their SHA is a PR head: a verified on-base tip remains valid, and an undelivered one cannot use the PR exemption.

Forge ref identities come from one unfiltered [`git/matching-refs/` response](https://docs.github.com/en/rest/git/refs#list-matching-references), whose GitHub contract returns the entire ref namespace without offset pagination. The guard does not assemble a ref snapshot from `/branches` or `/tags` pages: deleting an earlier entry can shift later offsets and hide undelivered work. A partial status, pagination or content-range header, malformed or duplicate evidence, or a missing or changed base branch refuses the close. Annotated tags are peeled by the captured immutable tag-object SHA under the same budget; only successful immutable resolutions are cached. Pull-request metadata still follows `Link` pagination inside the existing base bracket and digest; these separate forge reads do not form a transaction with the eventual status write.

Every ref outside `refs/pull/` remains in the snapshot and digest, including archive preservation refs such as `refs/preserved/<CARD-ID>/<branch>`. Additional namespaces must be on the base line only when their names carry this card; another card's preserved commits do not create a global ancestry refusal. Inventory rows must still be readable supported commit/tag objects. A card's preserved work therefore refuses the close even after the local branch, reflog and object have expired, and a new preservation ref between measurement and the write changes the digest. Raw internal `refs/pull/` refs are excluded, but an open or closed-unmerged PR whose `head.ref` names this card must have its head on the base line, even if only a pull ref retains that head. This refusal applies to same-repository and fork PRs; it grants no accounting exemption to fork heads. Delivered heads remain valid. Unrelated names and merged PRs add no ancestry requirement, so a squash-merged PR's historical head does not by itself block a close. Unmerged PR name, head or merge-state changes can cause a retryable refusal between measurement and the close write.

When the board knowingly abandons an unmerged proposal, the existing explicit cancellation path remains available: an authorized board actor can `PATCH /api/issues/{id}` with `{ "status": "cancelled" }` and a reason. Cancellation records abandonment, not Done or a zero-delta delivery, and does not remove the PR or its immutable pull ref. It does not bypass actor or review-policy checks. Merely selecting `record_only` does not certify abandonment or skip that form's independent ruling, workspace and evidence checks.

Forge deadline accounting uses monotonic `performance.now()`, with an injectable reader clock for deterministic tests, rather than wall-clock timestamps. Forward or backward wall-clock steps cannot shorten or stretch the snapshot budget. The 20-second write budget, 10-second per-call limit and serial write-read concurrency are unchanged; PR-list growth and a cold immutable-tag cache can still cause a timeout refusal.

The local inventory also includes unreachable commits, not only refs and common-directory reflogs. The hardened, read-only `git fsck --connectivity-only --unreachable --no-reflogs --no-progress` scan includes dangling `git stash create` commits and commits held only by a linked worktree's private HEAD reflog. Its commits join the measured local inventory and the close-write digest. An unreadable scan or exhausted shared Git deadline refuses; the scan never writes `lost-found`. This does not claim to exclude unreferenced blobs or trees, forged objects, or copies elsewhere on disk.

The final-stage PATCH preserves that proven measurement through the post-run-stop preflight and the locked preflight. Neither preflight certifies a delivery head. The locked worktree and forge recheck must still pass before the decision, Tier 2 audit, and `done` status commit together. Without a Tier 2 declaration, a Done PATCH still fails the tier gate; an ordinary final approval without delivery still fails the final-delivery preflight.

This proof describes the forge snapshot, not every recoverable copy on disk. A branch or tag off the base line blocks the close unless its exact tip is a pull-request head in this repository, in any state. An unrelated pull request can therefore account for work that this card does not link. Forks, deleted refs, dangling local objects, forged local objects, files in allowed regenerated directories, and copies outside the managed checkout are not delivery evidence. Local checks are refusal-only tripwires. A push after the last forge read remains outside the measured snapshot. Unrelated pushes between the two snapshots can cause a retryable refusal.

The no-workspace form (a card with no project and no execution workspace) adds these checks and refusals (SUP-24547). The close request's own `title` and `description` are checked as effective text, both at the measurement and under the row lock, so a close that carries a repository citation refuses even when the stored text is clean. The census reloads the database catalog on every proof (no process-wide cache), quotes and schema-qualifies every identifier it renders, and binds UUID and identity sets as one JSON parameter, so a catalog with mixed-case or reserved names, or a 22,000-UUID row, does not break the close. A row explicitly owned by another existing card (an explicit card column, or an issue-typed `entity_type`/`entity_id` pair) is not this card's evidence through a run, a soft reference or an indexed JSON selector; a direct explicit match on this card still refuses. A run whose `native_issue_id` is another card is not this card's run and does not seed its census. Run events are company-scoped and capped (2,000 rows, 32 MiB; more refuses), and a census row over 1 MiB, or a round whose rows pass the remaining 32 MiB card budget, is refused in SQL before it is transferred. Machine surfaces (runs, run events, receipts, native results) use the machine policy (a bare hex trace is not a SHA; a 40-character SHA, a cued SHA, a URL, a key or a reference is evidence); user-authored text uses the prose policy. Complete JSON text is parsed from the original before escapes are normalised. `projectedTotal` is not a project key (`projectId`, `project`, `projectWorkspaceId` are), and a generic `/tags/`, `/releases/`, `/branches/` or `/changes/` segment needs two parent path segments to count as a repository path. The guard's own `issue.done_transition_exclusion_below_threshold` row is allowed, and its details are still scanned. The `issue.done_transition_no_repository_landing_verified` audit carries `creationSnapshot`: `recorded` when `issue.created` recorded the project, project workspace and description, `not_recorded` when a legacy card was accepted on its current null project pointers.

Deleting a project cascades its project and execution workspaces and nulls those workspace pointers on cards; a direct `issues.projectId` reference instead restricts deletion. `DELETE /api/projects/{id}` writes a `project.deleted` activity row in the same transaction as the delete (the delete rolls back if the audit write fails). Its persisted `details` carry `affectedIssues` (`issueId`, `projectId`, `projectWorkspaceId`, `executionWorkspaceId`, capped at 5,000 cards), `affectedCount` and `affectedTruncated`. The affected set includes execution-only bindings and cards named by a deleted execution workspace's `sourceIssueId`, even if the card no longer has a workspace pointer. The published live-event and plugin payloads carry only `affectedCount` and `affectedTruncated`, never the issue list. `DELETE /api/projects/{id}/workspaces/{workspaceId}` follows the same pattern: its `project.workspace_deleted` row is written in the same transaction as the removal (rollback if the audit write fails) and carries the same `affectedIssues` (cards bound to that workspace directly or through its execution workspaces), `affectedCount` and `affectedTruncated`, with only the counts published. The no-workspace close refuses a card listed in a `project.deleted` or `project.workspace_deleted` row of its company, because it once had a binding. When either audit has `affectedTruncated: true`, a same-company card with null project/workspace bindings and no complete creation snapshot also refuses even if it is absent from `affectedIssues`: the deletion exceeded the audit cap, so a former binding cannot be ruled out. The refusal retains the board close remedy. This conservative fallback can refuse unrelated legacy cards in that company; other-company cards and cards with complete clean creation snapshots are not refused by the fallback. The repository-replacement path (`services/projects.ts` workspace sync) removes workspaces without this audit and remains an unattributed residual. Projects deleted before this audit existed keep the missing-snapshot compatibility path. The workspace deletion snapshot/lock-order race remains unresolved when the omitted card is not covered by a truncated audit. Unaudited heartbeat-run hard deletion can likewise erase evidence the close would have refused on.

A `record_only` card with no project, no project workspace and no execution workspace that the control plane shows never had one (SUP-24547) has no worktree to probe, so the same close form rests on the database half alone: the independent `entry-ruling` document (authored by a board member of the company, never an agent), no linked pull request, and a closed-world history check. The card is refused (422, with the board close path as the remedy) when any of the following is found: a row tied to the issue in any workspace table listed in `NO_WORKSPACE_REFERENCE_TABLES`; a heartbeat run linked to the issue by `heartbeat_runs.native_issue_id` or whose context names it, or naming a workspace, project, repository, branch or pull request, in its context, `result_json`, `usage_json`, stdout/stderr excerpts or `error`, or in `native_run_results.result_json` (hyphenated, plain, numeric and stringified-JSON spellings count); a comment, document revision, work product or activity row citing a pull request, commit SHA, Git ref or GitHub URL; an activity action or changed field outside the allow-lists in `done-transition-guard.ts`; an `issue.updated` row with a `patch` (a plugin host `issues.update`, which records no old value) that touches a title or description or any key outside the allow-list, even with a null value, or with neither `changes` nor `patch`. Any other card without an execution workspace keeps the refusal described above.

The same check derives a missing `issue.created` snapshot when the card's project and project workspace are still null and no audit row names a project. A later `issue.updated` `changes` entry for the title or description that has no `from` still refuses. A recorded change of 200 code points or more still refuses: a write-time scan of the full text is not stored yet, and that close stays on the board path.

The check scans every column of every row the live public-schema catalog attributes to the card, including comment metadata and columns on tables that also have dedicated history checks. Attribution follows issue and run foreign keys, conventionally named issue/run references (including arrays), unbound `*_id`/`*_key` columns equal to the card UUID or identifier, and indexed JSON text expressions. Run, agent and document references discovered in attributed rows expand the scan to a fixed point. Agent-linked rows must name this card in their contents and, when timestamp columns exist, have been created or updated since the card. A row reached only through a run or agent that belongs to another existing card is excluded; children linked only by `issues.parent_id` and company-only rows are not attributed.

Non-null project/workspace foreign keys and values equal to this company's project/workspace UUIDs refuse. A non-null opaque column also refuses rather than being ignored. The scan refuses above 200 attributed rows per table, 1 MiB per serialized row or value, 32 MiB per card, or four attribution rounds without convergence. Serialized-row accounting includes JSON keys and null fields. These are conservative admission limits, not database query-time limits; no supporting indexes or migration are added here.

A title or description that starts with `[` or `{` is prose. An unknown host with an ordinary path is not evidence. The word gerrit is not evidence; a Gerrit host or `/c/.../+/N` path is. A workspace key whose value is not provably empty is evidence, including a truncated key. Checkout, a preflight-blocked row, and a previous verified close are neutral audit actions and do not by themselves refuse. Deleting an agent keeps its comments, activity, runs and sessions and leaves the agent row as a tombstone (`status` `deleted`); that needs no migration. Company-only tables, attachments, and run-log text outside the database are not read at close time. A generic erasure ledger and write-time scan verdicts are not implemented: an unaudited overwrite or deletion can remove evidence, and text outside retained excerpts cannot be proved clean.

Deleted agents remain ineligible for assignment and invocation; both shared eligibility reasons report `terminated`, not `unknown_status`.

An ordinary `report`/`reportTitle` is not the abbreviated repository field `repo` (or its plural `repos`, including `repos_touched`); plain numeric values are neutral unless carried by an evidence field such as `pr`. A link on a `review` or `reviews` subdomain counts as repository evidence only when it has a repository citation path, is on a known forge domain, or has a Gerrit-shaped path (`/<number>`, `/q/`, `#/c/`); `https://review.example.org/policies/retention` is ordinary prose. A board-reopened card is checked again on re-close: the prior Tier 1 audit's typed `noRepositoryLanding` proof container is not itself a repository binding, but every field within it is still scanned. Prior verification records are retained, not exempted or deleted.

The PATCH also applies the pending execution-stage transition to the same issue update. If a pending review stage's stored status or assignee has drifted from its current participant, a PATCH that only sets `deliveryRequirement` can restore `status: in_review` and assign that stage's participant (clearing the previous assignee). Inspect the returned status, assignee, and execution state rather than assuming a classification-only mutation.

A refusal returns HTTP 409 with `approval_final_delivery_preflight`, the underlying named reason, `deliveryOwnerIssueId`, and an actionable `remedy`. Draft delivery requires the owner to mark the PR ready and submit the final review again. Missing delivery requires that owner to provide the delivery receipt/PR. The stage stays pending: no approved decision, completion, approval stamp, or merge arm is committed.

A delivery that merged every pull request before the final stage armed (a merge-first delivery flow) has no open PR left, so the `no-pr` remedy above cannot be met (SUP-25478). When the resolver and the merged-mention fallback both end in `no-pr`, the preflight reads the card's own `pull_request` work products. The same applies when the merged-mention fallback resolves one live-merged pull request but refuses it as `not_delivered: live PR is not the owner's recorded repo delivery`, because its head branch (now spent) is not the card's recorded delivery branch. That pull request is admitted only when it is the card's primary `pull_request` work product and every check below passes; otherwise the `not_delivered` refusal stands, with the merged-first remedy when those checks ran and refused. Work-product status and metadata are agent-writable, so they only name the claim and are never trusted alone. The preflight admits the final verdict only when all of these hold:

- The card has at least one `pull_request` work product, and every one has status `merged`.
- Exactly one is primary (or there is only one). The primary carries a full 40-hex `metadata.mergeCommitSha`.
- The control plane recorded the reviewed head as `executionState.approvalStatus.approvedHeadSha`. Agents cannot write it: `executionState` is in no issue update validator, and the server writes `approvedHeadSha` only from a head it resolved live on GitHub (the final-delivery preflight, the merge-arming anchor, the approval-status reconciler, the board head-approval route). Work-product `metadata.headSha` is agent-writable and is never used. A review-entry delivery record is not used either: a branch-only record carries an agent-asserted head, and a bound-PR record routes the resolver to that PR, so it never reaches this path.
- Every work product names a pull request (externalId `owner/repo#N`, or `metadata.repository` with `metadata.prNumber`) in the card's delivery repository. Letter case does not matter.
- Every distinct pull request is read live from GitHub. Each one must be merged, with its base repository and head repository both the card's delivery repository (no fork), merged into the card's recorded base branch (`base.ref`), with a readable `merged_at` time, and with a merge commit that equals any `metadata.mergeCommitSha` its work products record.
- The primary pull request merged at the recorded reviewed head (`approvedHeadSha`), and the head was recorded no later than the merge: `approvalStatus.approvedAt`, the time the server recorded that head, must be at or before the primary's live `merged_at`. GitHub reports `merged_at` to the second, so `approvedAt` is compared at second precision. A record in the same second as the merge is accepted, and a record in any later second refuses. A head recorded without a readable `approvedAt` is not a usable record.
- The primary passes the board landing proof (`verifyBoardLandingProof`), given the recorded merge commit and the recorded reviewed head. The proof requires the same merge commit and head, the card's repository by live name and immutable repository id, and board-written evidence that ties the PR to the card: a work product that only the board wrote. A board comment that names the PR does not unlock this path. The proof also requires the GitHub compare to show the merge commit on the card's recorded base branch, which must resolve as a live branch.
- Every pull request merged at or before the final decision row's `createdAt`. Each door inserts that row in its locked write transaction with the default `created_at = now()`, the transaction timestamp, so the locked preflight reads `now()` in the same transaction and compares the latest live `merged_at` with it. A later `merged_at` refuses, and the stage stays pending.

The decision then certifies no head. It is tagged `approvalStatus.finalDeliveryUncertified` with a `merged-before-verdict:` reason and the `mergeCommitSha`. The post-commit hook records `status:skipped:merged-before-verdict: …` with that merge commit, and it stamps and arms nothing. Merge-arming republish and the approval-status reconciler skip the decision with `head_uncertified`, as for any tagged decision. The done-tier guard still owns attribution: an agent close still needs an accepted Tier 1 or Tier 2 declaration. The existing stage-seat checks still apply, so an agent that is not the stage participant cannot record the verdict.

Every other case refuses as before. An open PR that resolves takes the ordinary certified path and arm. If any work product is recorded as not merged, the refusal and its remedy do not change. If every work product is recorded as merged but a check above fails, the preflight still refuses with `approval_final_delivery_preflight` and the `no-pr` reason, and the remedy names the missing field or the failed check. It does not ask for an open PR. A failed live check also returns `landingProofRefusal` with a named code and reason:

- `merged_first_pr_not_merged`: the PR is still open or was closed without merging.
- `merged_first_wrong_repository`: the work product or the live PR names another repository.
- `merged_first_fork_head`: the head is in a fork.
- `merged_first_wrong_base`: the PR merged into another base branch.
- `merged_first_reviewed_head_unrecorded`: the card has no recorded `approvalStatus.approvedHeadSha`, or that head has no readable `approvedAt`. The remedy names the missing record and points to an accepted `doneTransitionOverride` with disposition `merged-elsewhere`.
- `merged_first_reviewed_head_after_merge`: the reviewed head was recorded in a later second than the primary pull request merged.
- `merged_first_merged_after_verdict`: a PR merged after the final decision row's `createdAt`.
- `merged_first_stale_record`: a recorded merge commit is not the live one.
- `merged_first_head_not_reviewed`: the primary merged at a head other than the recorded `approvedHeadSha`.
- `merged_first_pr_unreadable`: GitHub returned 404, was rate limited, returned another HTTP error, timed out or failed on the network, or reported no readable `merged_at`.
- The `landing_proof_*` codes of the board landing proof.
- `merged_first_work_product_unmerged`: inside the write transaction, a linked `pull_request` work product is not `merged` (see below).

The whole preflight stays bounded by its 20-second timeout, which also refuses. The work products and live PRs are read before the write transaction, like the rest of the preflight verdict. Inside the write transaction, under the issue row lock, the preflight reads the card's `pull_request` work products again (`FOR UPDATE`). If any of them is not `merged` (for example an open PR work product added or reopened after the merge proof), the verdict refuses with `merged_first_work_product_unmerged`, a deterministic refusal, and the card does not go done. A work product inserted after that re-read, before the transaction commits, is not detected.

Every `approval_final_delivery_preflight` refusal also says whether it is deterministic for this delivery, in `details.deterministic` and in the remedy text, so a retrying agent does not turn a refusal into a `changes_requested` decision or a wake loop.

- A refusal is not deterministic (`deterministic: false`) when it rests on a GitHub read or a timing that can change: a reason that starts with `head_unverifiable:`, `unreadable_mention:` or `head_moved:`, or the codes `merged_first_pr_unreadable`, `merged_first_merged_after_verdict` and `landing_proof_unverifiable`. The remedy allows one more submission of the same final verdict.
- Every other refusal is deterministic (`deterministic: true`). The same final verdict is refused again until the delivery record or the pull request changes.

Both remedies name the lawful dispositions. A deterministic remedy names: fix what the refusal names and submit again; park the card blocked with an unblock descriptor that names the refusal; have a board user close the card through the board route (for example with an accepted `doneTransitionOverride`); or re-issue the final verdict after a server fix for the refusal deploys. A non-deterministic remedy names, for a repeat refusal: park the card blocked the same way; have a board user close the card through the board route; or re-issue the final verdict after the cause clears or a server fix deploys.

A stage approval over a card that owns no open PR is not refused while later stages remain (SUP-24085). Stamp eligibility ignores `post_merge` stages, so on an ADR-072 close ladder (a `pre_merge` review, then `post_merge` stages) the first approve is already stamp-eligible, and before this change a parent card with no PR of its own could not record it. Now, when the decision's resulting state is pending on a later stage that is not completed or skipped and the delivery verdict is `no-pr`, the PATCH verdict, approval comment, and board stage-decision doors record the decision, advance the pointer, and keep the card `in_review`. That decision certifies no head: it is tagged `approvalStatus.finalDeliveryUncertified` with its decision id, and the post-commit hook records `status:skipped:head_uncertified` without resolving, claiming a receipt for, or stamping any head, even when a PR is linked after the preflight. The same tag binds every later stamp writer: `POST /issues/:id/merge-arming/republish` refuses a tagged decision with `head_uncertified`, and the approval-status reconciler skips it with `head_uncertified`, before either resolves a head or touches a receipt. A tag from an earlier decision (its decision id differs from `lastDecisionId`) has no effect. An own PR that is closed unmerged resolves as `no-pr`: a stage approval that does not complete the card is admitted and tagged the same way, and the final approval still refuses. Every other unresolved verdict (draft, unreadable or moved head, ambiguous, not delivered, timeout) still refuses with `approval_final_delivery_preflight`, and a card or binding change during the preflight still refuses with `approval_final_delivery_preflight_stale`, as before. When the verdict resolves, the preflight still certifies `approvedHeadSha` and `finalDelivery` for that decision, so the pre-merge `paperclip/approved` stamp keeps its exact head. The escalation-accept door runs no preflight before the ladder completes, and the recovery-resolution door is a `done` close that the review-ladder guard refuses while stages remain undecided.

All five terminal approval doors resolve the delivery verdict (bounded by a 20 s timeout) before their write transaction or interaction acceptance; no GitHub request runs under the issue-row lock, except the zero-delta close, which re-reads its forge snapshot under a 20-second budget while the row is held. Under that lock, each door that holds a repository-delivery prefetch compares the certified issue `status`/`updatedAt`, `assigneeAgentId`, `assigneeUserId` and `executionPolicy` (agent ids in stage participants and `stallEscalation.toAgentId` compare case-insensitively; user ids and assignee columns do not fold, see [execution policy](guides/execution-policy.md)), the `deliveryRequirement` classification, and database delivery binding (repo context, delivery-branch ownership, recorded PR identity, and the certified PR's repo) against the preflight values. A final escalation that starts as `record_only` holds no prefetch, so the locked preflight returns before those comparisons; on that path the route compares only the `deliveryRequirement` classification, and a concurrent assignee or execution-policy change does not reject the approval. A `record_only` PATCH compares only the `deliveryRequirement` classification under the lock, so a concurrent assignee or execution-policy change does not reject it. PATCH and approval-comment auto-close check before persisting the decision; final escalation acceptance checks and then records its decision in the interaction service's transaction, so a stale verdict leaves the interaction pending. For a PATCH that must release its own run first, the route verifies that no other issue field or delivery binding changed during that release, then takes one certificate from the post-release row before entering the transaction. It never re-anchors an existing certificate. Escalation acceptance defers its activity and post-commit actions until the interaction transaction commits. A changed certified card or binding returns HTTP 409 `approval_final_delivery_preflight_stale`; the stage stays pending with no approved decision, receipt publication, or merge arm, and the caller retries.

The agent-id case fold in these compares decides only whether the card changed under the lock. It does not decide who may approve. The actor-versus-seat check and stage membership compare agent and user ids exactly, so an agent whose id matches the seat or a stage participant only by letter case cannot approve; see the boundary in [execution policy](guides/execution-policy.md).

Agent mutation authorization can adopt a stale checkout into the request's live run before PATCH's first certificate. The pre-certificate guard permits only that exact run-link transition when the resulting issue timestamp equals its execution-lock timestamp; unrelated card or delivery changes still refuse. The locked guard compares the resulting certificate to the issue and binding at commit, including any later `updatedAt` change.

An approval comment that interrupts an active run reloads the issue after cancellation releases the run links and may update `updatedAt`. It evaluates the review stage and certifies delivery from that post-interrupt row. A later change during the external preflight still fails the locked recheck.

The check runs on the PATCH verdict, board stage-decision, auto-approval comment, recovery decision, and final escalation-accept routes. Repository-free doc/gate cards retain their existing close semantics. Sanctioned no-deliverable-head overrides remain subject to the existing done guard; they do not bypass ladder or tier requirements. An accepted `doneTransitionOverride` lets an unresolved delivery verdict pass the preflight on the PATCH and recovery-decision routes alike, so an accepted override does not end in `approval_final_delivery_preflight`.

## Done-close draft safety

The done-transition guard includes linked drafts when checking Tier-1 `landing-delegated` declarations and plain (non-approval) closes. Only an open draft whose PR base repository and verified head repository match the card's delivery repository, and whose branch or title identifies the card, receives the named `head_draft` refusal. The HTTP remedy and refusal comment tell the owner to promote it out of draft; a cited, moved, forked, or other-repository PR is not this card's draft delivery. A missing head repository cannot prove draft ownership. Approval-carrying closes keep the preflight's `approval_final_delivery_preflight` / `head_draft` refusal, except that a `head_draft` that rests only on cached open+draft mentions is revalidated live (SUP-24033): if live state shows the card's sole owned mentioned PR merged, the preflight uses the verified merged-carrier path instead (a draft cached without a head branch is judged for ownership on the head branch its live read reports; a cached head branch is never overridden, SUP-25333), while any live draft that discovery or the mention reads can see still refuses. A draft that discovery cannot see (it sits past the part of the list that was read, or its list entry is malformed) is never assumed absent: in that case the revalidation is not used and the base `head_draft` refusal stands. The revalidation applies only when live discovery read every cached draft's repository completely. Discovery reads page 1 of the open-PR list only (100 entries, no `page` parameter), so a repository counts as read completely only when that response is a short page, has no malformed entry, and has either no `Link` header or a `Link` header that parses fully, has a `rel` in every link-value, has no other parameter, names only `rel="self"`, and whose self target is page 1 of this exact request (same origin, path and query, `page` absent or `1`; a relative, empty, other-host or other-page target does not count). An entry is malformed when it is not an object or when any field that discovery reads is not valid: `number` a positive integer, `head.ref` a string, `title` a string, `draft` a boolean (a non-conforming entry may have been an owned live draft that discovery would drop). Any other `Link` header (`next`, `last`, `prev`, `first`, `previous`, an unknown relation such as one a proxy adds, a link-value with no `rel`, an extra or extended parameter, a self link to another page, host or query, an empty or malformed header) leaves the page unread: a real GitHub page-1 response never carries `prev` or `first` and carries `next` and `last` when more pages exist, so those relations mean more pages or an altered response. A page that is not proven complete means a live draft past it cannot be ruled out, and the `head_draft` refusal stands. A proxy that adds a `Link` relation outside this whitelist therefore costs the revalidation for that repository (the refusal is the base behaviour); a proxy that drops the `Link` header from a list with more pages cannot be detected and is an accepted residual. It also applies only when the card cites at most 5 PRs, and a carrier that passes the live checks still takes the full live merge verification, whose own refusal reason is then returned. On successful live hydration, discovery and ownership use the current branch, title, head repository and draft state instead of stale mention identity; without GitHub credentials, previously refreshed cached evidence remains eligible.

Draft ownership requires a resolved card delivery repository. A linked PR's own base and head repositories matching each other cannot establish ownership when the card's repository is unknown; the backstop leaves that `done` card unchanged.

For older cards already closed `done` over a draft, the hourly done-close landing backstop parks the card `blocked` after its 24-hour grace with a board-owned action to mark the PR ready and republish approval at the ready head. A previously confirmed merged sibling still participates in each later sweep's card-level landing verdict: a remaining draft is audited as superseded, never parked. A missing live head repository cannot establish ownership and leaves the done card unchanged. The park precedes notification; a failed update leaves the done card eligible, and a failed comment leaves the blocked park discoverable even after the seven-day done lookback. The draft-stranded audit marker follows successful comment and assignee wake so an interrupted notification retries. The carrier promotion sweep keeps done parents (not cancelled ones) eligible for its three-day age cap, but only promotes a draft in the parent's delivery repository after two live reads verify its open draft state, head repository and exact branch, and unchanged cached head SHA. A per-company/PR database advisory lock serializes the ledger check, GraphQL ready mutation and durable activity row, so concurrent sweeps produce one promotion record. GitHub's ready mutation accepts no expected-head compare-and-swap: a head change after the final live read remains a remote race. These paths do not publish approval or arm a draft merge.

## Done-close carrier re-check

A Tier-1 `landing-delegated` close re-reads the named carrier PR before the guard accepts it (SUP-24135). The guard sends one read-only GitHub GraphQL query with the token that already serves the auto-merge and merge-queue probes. The query reads the head commit's required checks (`isRequired` for this PR) and `mergeStateStatus`. The guard refuses the close in two cases:

- `carrier_required_check_failed`: a required check run concluded `failure`, `timed_out`, `cancelled` or `startup_failure`, or a required commit status is `failure` or `error`, and no other run of the same check can still pass (a re-run in progress keeps the close allowed). Check runs and commit statuses are separate requirements: a passing status does not hide a failed check run with the same name. The refusal names at most three failed checks, each cut to 80 characters.
- `carrier_merge_conflict`: `mergeStateStatus` is `DIRTY`.

The query reads one page of 100 check contexts. When GitHub reports a next page, or does not report the page boundary, the guard does not refuse on checks: a rerun past context 100 can still pass. A merge conflict still refuses.

`BLOCKED` alone does not refuse: it is the normal state while required checks run or a review is pending. `UNKNOWN` does not refuse: GitHub is still computing it. A merged or closed PR, a failed hydration, or an unreadable probe (non-2xx, GraphQL errors, no token, or no answer within 10 seconds) also does not refuse, because a refusal must rest on live proof. The probe runs only at close time. A carrier that fails after the close stays with the hourly done-close landing backstop and its 24-hour landing verdict.

## Record-only Tier 2 pass contradictions

A `record_only` live close uses `Closed at Tier 2 (live): record-only probe ` followed by a backticked command, `target <observed target> observed <UTC ISO-8601 timestamp> result: pass <pass predicate and observed result>` (or the existing UTC observation range). The structured `doneTier.probeEvidence` carries the same evidence without the close prefix. No merge head is required.

Send one declaration source: the canonical line in the comment, or the structured `doneTier` with no line-start canonical declaration in the comment (the server then appends the rendered line). A close that carries both is accepted only when the comment holds exactly one canonical declaration line and it equals the line the structured field renders to; the original comment is kept, so one declaration persists. Every other dual-source close (sources that differ, either source malformed, several declarations in the comment, or a canonical prefix inside `probeEvidence`) is refused with 422 `done_tier_dual_source_conflict` before anything is rendered or written; the guard never removes a caller declaration to accept. This applies at issue PATCH, comment auto-approval, recovery-action resolution and the structured system-backstop close (`resolveDoneTierDeclarationSources` in `server/src/services/done-transition-guard.ts`). The response reports each source's status, the differing field names and bounded excerpts in which the command and every free-text field are replaced by length markers.

The guard refuses a `result: pass` declaration with `done_transition_record_only_probe_contradiction` when its trailing predicate/result contains one of these eight token-anchored markers (case-insensitive except `REFUSED`, which matches uppercase only):

| Marker name | Recognized form |
| --- | --- |
| `exit_nonzero` | `exit <number>` with a nonzero value |
| `exited_nonzero` | `exited <number>` with a nonzero value |
| `failed_positive` | `failed=<number>` with a positive value |
| `scanned_zero` | `scanned=<number>` whose value is zero |
| `non_clean` | `non-clean` |
| `failed_closed` | `failed closed. All` or `scan failed closed on all 4 repos` (literal probe-failure contexts) |
| `refused` | `REFUSED` |
| `partial_failure` | `partial failure` |

A `<number>` is one complete signed decimal token (integer, fraction such as `.5` or `0.5`, or exponent form such as `1e2`) judged by its numeric value, not by an integer prefix: `scanned=0.5`, `scanned=1e2`, `failed=0.0`, `failed=-1`, `exit 0.0`, and `exit -0` do not contradict a pass, while `scanned=0.0`, `scanned=-0`, `scanned=0e5`, `failed=1.5`, and `exit -0.5` do. Words have word-boundary anchors; phrase separators accept spaces or tabs. Lowercase `refused` (for example `anon request refused 401`) and a bare `failed closed` (for example a predicate confirming an expected negative path) do not contradict a pass; a failed-closed outcome with an explicit failing exit is caught by the `exit`/`exited` markers. This is a bounded marker list, not arbitrary prose inference: it checks only the declaration's predicate/result, not the probe command, target, or unrelated comment text. `exit criteria met`, `exit 0`, `exited 0`, `failed=0`, and `scanned=42` do not contradict a pass. `result: fail` remains refused by the existing failing-predicate rule.

The added `scan failed closed on all 4 repos` context names the failed scan itself even when no exit code or failed count follows it. It does not turn bare `failed closed` into a contradiction marker. A clean declaration with `scanned=4 failed=0 matched=29 armed=0 exit 0` can still close when separate vet lines in the comment report `REFUSED missing paperclip/approved; exit 1`: those lines describe another operation outside the matched declaration predicate.

The refusal names the marker, persists the same specific code (`done_transition_record_only_probe_contradiction`) as `details.code` of its `issue.done_transition_refused` audit row, repeats the accepted form verbatim, and states the honest alternative: **Report the non-clean cycle and do not close.** Re-probe before claiming a genuine pass; do not relabel a failed probe to force a close.

Every accepted Tier 2 record-only close retains the existing machine-readable `issue.done_transition_tier2_close` activity row with `details.tierForm: "record-only"`, probe evidence, observation, and closing-run identity. The row commits atomically with the terminal status, including approval and system-backstop closes. Count that action and `tierForm` to count this class. No contradiction is accepted, so no `issue.done_transition_declared_pass_with_failed_evidence` row is needed.

## Certification and publication

The decision transaction persists `executionState.approvalStatus.approvedHeadSha` and `finalDelivery` (`owner`, `repo`, `number`, `headSha`, `displayName`) from the preflight. Credentials are never persisted in that anchor. The post-commit hook uses this certification instead of certifying a later live head. `finalDelivery` is tagged with the decision id and every decision patch clears any prior-cycle `finalDelivery` first, so the hook only trusts a certification whose `decisionId` equals the card's `lastDecisionId`; a terminal approval that skips the preflight (sanctioned override accepted, repository-free) re-resolves the live head instead. The escalation-accept door mints its decision id inside the shared decision helper, so it re-tags the preflight certification with that id before running the hook. Publication remains delivery-identity-gated and pinned to both the reviewed SHA and repo/PR identity.

The GitHub PR head is externally owned: it is not re-read under the database row lock. If it moves between preflight and publication, the head-pinned publisher returns `status:skipped:head_moved`, writes no status on the new head, and suppresses merge arming. A separate design card covers recertifying the external head at the approval door. If publication instead resolves a different PR than the certified one (same-SHA sibling), it returns `status:skipped:delivery_moved` with the same no-status, no-arm result. The original approved-head anchor survives for the reconciler's existing Guard A content-identity check. Changed content needs fresh review; pending, cancelled, skipped, or incomplete ladders are not approval.

No ruleset, workflow, required context/app pin, override label, allowlist, or merge-authority hard stop changes. AS-03 consumes certified anchors; this change does not manufacture approval for an already-stranded card.
