# Approval-status reconciliation

The approval-status reconciler repairs terminally approved cards whose `paperclip/approved` status was not published or was lost after the approval decision.

## Candidate admission

A candidate must have a terminal approved ladder and a persisted approval anchor. Linked GitHub pull requests are normally admitted only when their cached snapshot is open and non-draft. A cached `draft: true` snapshot is also admitted when `executionState.approvalStatus.approvedHeadSha` or `executionState.approvalStatus.publishedHeadSha` is a non-empty string. That exception is only a reachability recovery path: cached metadata is not authoritative for the current PR state.

## Live validation

For every candidate, the reconciler reads the pull request from GitHub before checking the commit status or publishing anything. The live response is authoritative for state, merge status, head SHA, and draft state. A live draft PR is refused with no status write, even when the cached snapshot is stale or an approved head anchor exists.

The live head must equal the certified head, or Guard A must positively prove content identity. It accepts unchanged PR-diff blobs (including an approved subset absorbed into the base), identical commit trees, or identical complete per-file patches with only hunk positions changed. Patch identity preserves significant whitespace, filenames, and change metadata; missing/binary/truncated patches are not patch proof. Compare lists at GitHub's 300-file cap are incomplete and cannot prove equivalence. Substantive changes still refuse automatic publication.

The delegated publish pins the exact PR and expected head. For a certified head change, only the head component of a recorded delivery binding is superseded: its repository, branch, source card, and PR number remain enforced. The delivery receipt is waived only when the decision carries a certified `finalDelivery` naming that same PR (the explicit decision pins `expectedPr` to it); a card without a matching certified `finalDelivery` still needs an exact-head delivery receipt, and a missing one refuses with `delivery-receipt-missing`. A further push before the publisher's head read refuses instead of stamping another head.

## Idempotency and failure behavior

The reconciler first checks the live commit status. An existing successful `paperclip/approved` status is treated as already repaired and is not published again. Missing or failed GitHub reads are recorded as failures and retried by a later tick; uncertain validation never publishes.

The recovery path preserves the existing scan cap, cursor, per-head behavior, delivery-identity checks, ladder guards, and merge-arming rules. It does not reopen review, alter approval content, or create a local GitHub status.

## Reviewing a changed head after completion

The completed ladder is not reopened. Use these company-scoped control-plane APIs:

- `GET /api/issues/:issueId/merge-arming/head-review` returns the certified head, live head, Guard A delta, approved/live file records and patches, and a compare link. This is read-only.
- `POST /api/issues/:issueId/merge-arming/approve-head` records a separate head decision and publishes `paperclip/approved` for exactly the submitted head:

  ```json
  {
    "approvedHeadSha": "<40-character certified SHA from the preview>",
    "headSha": "<40-character live SHA from the preview>",
    "reason": "Reviewed the post-ladder delta and its verification"
  }
  ```

Both APIs require board owner/admin authority (including trusted-local/instance-admin board context). All agent actors are refused before issue lookup or GitHub access, including the original reviewer. Being the author, assignee, a reviewer, or a user with ordinary membership grants no head-approval authority.

The card must be `done`, every declared stage completed, the last decision approved, and Guard B stage integrity intact. Missing anchors, unverifiable deltas, non-open/draft PRs, stale preview anchors, moved heads, foreign delivery identities, and unauthorized actors refuse without a status write. The response includes the reviewed delta and publication outcome. The activity event `issue.approval_head_decision` records the actor, previous and requested heads, PR, reason, and Guard A summary before publication; audit failure prevents the write. Successful publication updates only `executionState.approvalStatus`, preserving the card status, ladder, and stage decisions.

### Head-bound merge release (SUP-20772)

A card-bound PR that cannot get a stamp through the normal path (a receipt that cannot exist, a head that was never stamped) is released by a board owner/admin, not by a waiver line. There are two routes. The default one re-publishes only what the card's own review already decided on that exact head. The override is for every other case, and is a separate, separately audited action:

- `POST /api/issues/:issueId/merge-arming/release` with `{ "headSha": "<40-character live SHA>", "reason": "..." }` publishes `paperclip/approved` with the control-plane `tea-core` App installation token and no other credential (so the `tea-core[bot]` creator check in `scripts/ci/check-paperclip-approved.sh` accepts it). Unlike other stamps there is no PAT, project-env or fleet fallback: with no App credential the route answers 409 `failed` and writes no status. The status description is `released by <actorType>:<actorId> for <sha>: <reason>`, cut to GitHub's 140 characters.
- The target is the PR in the card's verified delivery identity (`executionState.delivery`: project repo, control-plane delivery branch, PR number and URL). A PR that is only cited on the card is never a target; a card with no verified binding answers 409 before any GitHub access. The PR must be open, not a draft, still on the bound branch, and `headSha` must be its live head. A different or stale head, or a moved branch, answers 409 with no write. Agent actors and board members who are not owner/admin are refused before any GitHub access.
- The default route releases a card only when the card has a completed approving ladder where `headSha` equals either `approvalStatus.publishedHeadSha` or `approvalStatus.approvedHeadSha` (both are heads the card's own review decided), or a certified delivery (`approvalStatus.finalDelivery`) for this PR at `headSha`, provided the decision the certificate names (`decisionId`) was itself an eligible approval under the decider rules below (the certificate is not exempt from them: a certificate minted by an author, an unattributed decision, or a decider who has since left does not release). "Completed approving ladder" is the one the head-approval route (`approve-head`) requires: the card is `done`, the last decision is `approved`, the execution policy has at least one stage and every stage is completed, and the stage decisions pass `evaluateStageIntegrity` (a completed stage with no decision, a skipped stage and a stage decided by the return assignee all fail it). On top of that, for every stage in the policy the LATEST decision must be an approval, must be attributed to someone, and must not be by any of the people who authored the work (the return assignee, the delivery author and the creator agent, taken together, not only the one the integrity check resolves). A rejecting, unattributed or shadowed history fails, and so does a policy stage that is not an object. A cancelled card, a card that was never approved, an empty or missing policy, an incomplete ladder, a ladder whose decisions fail the integrity check, a certification for another head and a ladder approved on another head all answer 409 before any GitHub access. The audit rows carry `basis` (`certified_delivery` or `approved_ladder`).
- A card with a pending `post_merge` stage is not done, so its ladder cannot be a completed one: the default route's ladder basis requires a done card and every stage completed, as the board ruled, and does not narrow that to pre-merge stages. Such a card is released on its certified delivery (the review's `finalDelivery`, no done status needed) when it has one, or through the override route. The stamp itself (`paperclip/approved` from the normal path) is not held back by `post_merge` stages; that is `ladderIsTerminallyApproved`'s job and is unchanged.
- Eligibility and target are resolved again inside the publication lock, right before the status write and again before each retry. A card that was cancelled, whose approving decision was reversed, or whose delivery binding was retargeted after the first read is refused (`eligibility-changed`) with no write, so the old target is never released. The re-check runs on the lock's own database connection, so a release never needs a second pool connection while it holds the lock; releases of one head cannot deadlock the pool, whatever its size. The already-approved answer re-reads the live PR after its status lookup and is not given when the head moved.
- `POST /api/issues/:issueId/merge-arming/release-override` with `{ "headSha": "<40-character live SHA>", "overrideReason": "<written reason, at least 10 characters>" }` is the only way to release those cards. The default route does not accept `overrideReason` (400), so the default call cannot reach it. It has the same board-owner/admin check, delivery binding, certified-PR pin, live-PR checks, control-plane App credential, head binding and serialization, and publishes the same `paperclip/approved` status (its description reads `released by <actor> for <sha>: override: <reason>`). It writes its own audit rows: `issue.merge_release_override_requested` before the GitHub write, then `issue.merge_release_override` or `issue.merge_release_override_outcome`, with `basis: override`. It widens what an owner/admin key can release; the audit rows are accountability after the fact, not a prevention.
- Idempotent: a head whose newest `paperclip/approved` is a success created by the control plane answers 200 `already_approved` with no second status write, unless that success is a release this card never confirmed (see "Only a confirmed release is consumed" below), in which case a new, confirmed one is written; and only after the live PR has been read and found open, non-draft, on the bound branch and at `headSha`. Releases of one head are serialized (a Postgres advisory lock per company, repo and head), so two simultaneous requests write one status: the second answers `already_approved`. A success from any other creator, or a newer non-success, does not count: the release is published and logged as normal. The intent is recorded as `issue.merge_release_requested` before anything is written to GitHub (if that insert fails, nothing is published). The outcome follows: `issue.merge_release` for a fresh write, `issue.merge_release_outcome` (with `outcome` and `message`) for a refusal, a failure or an already-approved answer. If only the outcome insert fails, the status is still out, the response still reports it with `auditRecorded: false`, the error is logged, and the intent row names who released which head. The response always carries `auditRecorded`.
- The status is keyed by SHA, so a push after the release gets no stamp; release the new head. The live PR is re-read immediately before the write (after the status read) and again before each retry of a transient write failure, and a head that has moved is refused with no write. GitHub has no compare-and-swap on a commit status, so a push landing between that last read and the POST can still leave one status on the old SHA; it never covers the new head. The head is read once more after the write, and a head that moved is answered 409 with outcome `stale` (audited as an outcome row, not as a release), never as 200 `released`; the success status that was written to the old head is then set to `failure` (if that second write fails, the message says so). The final check is full liveness, not only the SHA: a PR that was closed, drafted or moved off its branch right after the write is `stale` too. The one exception is a PR that was merged at exactly the released head on the bound branch: auto-merge was waiting on this status, so the release took effect, and it is confirmed and answered `released` with no failure status. A PR merged at a different head or on a different branch is `stale` like the rest. A PR that is already merged, closed or drafted before the write is still refused. Only the old head is written to: the new head never received this release, and a failure written there could revoke a genuine approval on it, so it is left alone. If that re-read itself fails, the answer is 409 with outcome `failed` (`status:failed:post_write_pr_read:`), saying the status WAS written but the head could not be confirmed; it is audited as an outcome row, never as a release. A throwing prerequisite (secret lookup, token resolver) is recorded as a `failed` outcome row tied to the intent row (`intentId`). The status carries no `target_url`.
- The release keeps the card's certified boundary: if the card has a certified final delivery (`approvalStatus.finalDelivery`), the bound PR must be that PR, otherwise the route answers 409 and reads nothing from GitHub.
- A board release does not authorise a re-arm. The approval-status reconciler and the done-close landing backstop (the other consumer that enables auto-merge from a `paperclip/approved` success) both ignore a release-described success unless the card has a certified final delivery for that same repository, PR and head AND the release was confirmed (next bullet), so a release cannot turn into an auto-merge for an uncertified card. The backstop also reads the approval strictly: only the newest `paperclip/approved` status counts (a later failure revokes an earlier success, including the compensating failure above), and it must have been written by the control plane, so a forged ordinary success does not stand in for a certificate.
- Only a confirmed release is consumed, and only a confirmed release is accepted by CI. The publisher records `approvalStatus.releaseConfirmation` (`owner`, `repo`, `number`, `headSha` and `statusId`, GitHub's id of the status it wrote) as the very last database write of a release, on the lock's own connection, after the live head was re-read, the card's eligibility was re-checked once more after the write, and both still held. The reconciler and the backstop accept a release-described success only when its id equals that `statusId` and the record's repository, PR and head equal the card's certified delivery and the live head. A release whose confirmation is unknown therefore has no record and is never consumed: a status write that timed out or lost its answer, a head that could not be re-read, a card whose eligibility changed while the write was in flight, a status whose id GitHub did not return, a failed void, a process that died mid-release, and a second release status written by a duplicate whose answer was lost (a different id). The CI check cannot read the database, so the control plane tells it on GitHub: after the confirmation is committed it writes a second status, `paperclip/release-confirmed`, with the description `confirms status <id>`, as the same `tea-core[bot]` creator. With `PAPERCLIP_CARD_WAIVER_RETIRED=1`, `scripts/ci/check-paperclip-approved.sh` accepts a release-described success (description starting `released by `) only when such a marker, from the control-plane creator, names that very status id; without it the success is reported `UNCONFIRMED RELEASE` and treated as not approved, so a success that was voided, never confirmed or whose confirmation never committed is not an approval for CI either. With the switch OFF (the shipped default) the script reads, judges and prints exactly what the fold's script does: it does not read the description or the id, and it does not look for the marker, so until the switch is armed CI still accepts a release-described success without one (the server-side consumers do not). The marker is written only after the commit (never before), so a failed or abandoned release never has one; if the marker write fails the release answers `released` with a message saying CI does not accept it yet, and the next release call (which answers `already_approved`) or the reconciler's sweep re-writes it, idempotently; the reconciler looks for the marker on the statuses list and applies the same creator check CI does, so a status of that name from anyone else neither counts as the marker nor suppresses the repair. `paperclip/release-confirmed` is read by the script and is not a required check.
- The decider of each required stage must still be a current member of the card's company: an agent of that company that is not terminated or awaiting approval, or a user with an active membership in it. A user must still exist (an active membership whose user row is gone does not count); a removed user, a user of another company, an agent of another company, a terminated agent and the card's own creator (agent or user) all fail. Decisions of one stage are ordered by time only. The database records no order among decisions that share an instant, and no card-wide pointer stands in for one (the card's `lastDecisionId` is not used): every decision at the newest instant of a stage must be an eligible approval, so a tied rejection and approval, or a tied approval by an ineligible decider or by an author, refuses in either id order. (The shared integrity check the reconciler also uses, `evaluateStageIntegrity`, is unchanged and still represents a tie by its larger id; because the release then checks every tied decision itself, its answer does not depend on which id that is.)
- The release path has one end-to-end deadline, `totalMs` = 60 s, started when the request arrives, before authentication: a small middleware (`releaseRequestClock`, mounted ahead of the actor middleware) answers 409 (`status:failed:deadline`, nothing published) when the clock runs out while the request is still waiting to be authenticated, and the handler, if it ever runs, finds the clock expired and does nothing (no read, no write, no audit row); otherwise the handler is given the time that is left. The stuck authentication query itself runs on the shared pool and is abandoned, not cancelled. The handler's database work (issue lookup, owner/admin check, card check, intent audit row, credential lookup, publication lock transaction, re-checks) runs on one dedicated connection (`createRequestScopedDb`, not the shared pool). On a direct or session-mode connection the deadline ends that session on the server (`pg_terminate_backend` over a short-lived connection of its own): a statement or lock wait stops, the open transaction rolls back and the advisory lock is freed even if another session still holds the lock it waited on, and the connection carries server-side `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout`. Behind a transaction-mode pooler (`DATABASE_PREPARED_STATEMENTS=false`, which rejects startup parameters and maps no client to one backend) the connection is tracked instead: at the deadline every statement it started is cancelled with the driver's cancel request and the connection destroyed, with no server-side timeouts. The `AbortSignal` also cancels every GitHub request and stops the retry loops; each GitHub call is given up on after 10 s; no status write is started after the deadline. A success that may already be on the head when the deadline interrupts the release is voided on the compensation clock (`compensationMs`, 15 s) while the publication lock is still held, then the session ends. The outcome audit row has its own 15 s clock and its own connection, cancelled the same way (`auditRecorded: false` after that). Once the release is writing its confirmation (the seal) the deadline no longer abandons it: that write is bounded by its own 15 s statement timeout, then it either commits (answer `released`) or does not (answer `failed`, the success voided). Worst case from the arrival of the request: about 60 s, plus at most 15 s for a confirmation write that had begun, 15 s for the marker write and 15 s for the outcome row, so about 105 s. What is guaranteed is a finite answer and no late effect: nothing the request started commits after its answer. What is not cancelled: the stuck authentication query (abandoned), and a stuck secret provider call, which an abort signal cannot reach; its late answer is dropped and starts nothing. On a pooled connection a cancel request depends on the pooler forwarding it. A client that was not made by `createDb` has no connection settings to reuse; the route then falls back to the shared pool and abandons such waits.
- A success that cannot be confirmed is voided: if the PR cannot be read after the write, if the card is no longer eligible after the write (`status:stale:eligibility-changed-after-write`), if GitHub does not return the status id, if the confirmation record cannot be written, if the transaction is interrupted (the deadline, a statement timeout, a failed commit) after the write may have happened, or if the write itself got no answer at all (a timeout, a dropped connection, the deadline), a `failure` is written to the same head (the newest status decides) and the answer is `failed`; the board can release again. A release that answered `failed` or `stale` never commits a confirmation afterwards: the confirmation is written only by a release that is still open, in a short seal that the deadline does not interrupt and that answers for itself, and a release the deadline abandoned has its connection ended and cannot reach that write. If the void write also fails the message says so; the success then stays on the head with no confirmation record and no marker, so the reconciler and the backstop do not consume it and the CI check does not accept it (it needs the marker), but the success itself remains visible on the head until a newer status replaces it. The head that moved is handled as before: `stale`, with a `failure` on the old head.
- The merge is armed only for the head that was authorized, by every actuator, and only while the authority still holds. The done-close landing backstop, the approval-status reconciler's re-arm and the decision-time arm all pass the authorized head to the `enablePullRequestAutoMerge` mutation (`expectedHeadOid`), so GitHub refuses it if the PR's head is anything else; the clean-status fallback, which merges directly, merges that same verified head (and not the card's recorded head, which can be older) and is skipped (`skipped:head-mismatch`) when the two differ. Head binding cannot see approval state, so the authority is guarded separately: the backstop and the reconciler create an authority guard just before their own final read of the card, and `armMergeOnApproval` creates one at its start otherwise. The guard fingerprints the card's record (cancelled, stage ladder, completed stages, last decision, approved and published heads, certificate, release confirmation), every decision row and the standing of each decider (whether an agent is still a current agent of the company, so its ordinary idle/running/paused churn is not a revocation; a user's membership), and also requires that the newest decision of every pre-merge stage that has decision rows is an approval by an agent that is still a current agent of the company. It is checked before the first enable attempt and before EVERY retry of the mutation (a retry is not a new decision), and before a direct merge. A revocation that commits inside the GitHub call itself cannot be seen before the call, so the guard is checked once more after an accepted enable, and if it no longer holds the arm is taken back with `disablePullRequestAutoMerge` (`failed:authority-revoked ... auto-merge was disabled again`, or a message saying it could NOT be disabled and must be disabled by hand). A direct merge cannot be taken back; its guard is the check immediately before it. A success left on an old head cannot arm a newer one, and a revoked approval is not armed by a retry.
- Retiring the waiver in CI has a residual bypass that this route does not close: the CI check judges card binding from the author-chosen head ref and author type from GitHub's `user.type`. See "Known residual bypass" in [branch protection](branch-protection.md) before setting `PAPERCLIP_CARD_WAIVER_RETIRED`.
- A "release-assurance seat" has no server identity today, so the route is board-only. A seat that needs it acts through the board token.

The head decision is durable before the external status write. If GitHub accepts the status but storing publication state subsequently fails, the API reports the failure and the decision audit remains; a database rollback must not erase the authorization for an already-written status. The `issue.approval_head_decision` row records the authorizer, not that publication applied: a refused publication (for example `delivery-receipt-missing` or a moved head) is visible only in the 409 response, and no publish-outcome audit record exists yet.

## Override label and the reconciler

A PR carrying `override:paperclip-approval` (see [branch protection](branch-protection.md#override-label-sup-20897)) clears the CI enforcer without a `paperclip/approved` status. The reconciler is unaffected: it reads and writes only the status, never the label, and an overridden PR gets no status. Do not publish one to "match" the override. If the control plane later approves the head, the stamp passes the enforcer on its own and the label is not consulted.

## Release-assurance control plane (shadow mode)

Release assurance (RA) gets its own approval seat and a distinct `release-assurance/approved` status, separate from the normal ladder and from `paperclip/approved` (SUP-20771). This slice ships the control plane in **shadow mode only**: decisions are recorded and visible, but nothing is admitted and no RA status is ever written to GitHub. The database can only express `publication_mode = 'shadow'`, so turning publication on is a deliberate later migration, not a flag.

- `release_assurance_events` is an append-only ledger. Its company and issue foreign keys have no delete policy, so deleting a card or company that still has ledger rows is refused with 409 and the audit trail is kept. The ledger is append-only in the database: UPDATE, DELETE and TRUNCATE are revoked from the serving role and UPDATE and DELETE are rejected by a trigger for every role, and the issue key is composite with the company so a row cannot pair an issue with another company. This holds against the serving role and ordinary SQL, not against a table owner or superuser: those can still change rows by disabling or dropping the trigger, by `session_replication_role = replica`, or by `TRUNCATE` (including `CASCADE`). Production must run the application as the restricted serving role. The enrolled RA seat is stored as a plain recorded id, not a foreign key, so it survives deletion of the agent. `hold` is the board enrollment of a card and its exact recorded-delivery PR and persists across head changes; `go` and `no_go` are decisions bound to one exact lowercase 40-hex head. A revocation is a `no_go` on that head. `(company_id, event_id)` is the idempotency key: an identical replay returns the recorded event, a different payload under the same event id is 409.
- `POST /api/issues/:issueId/release-assurance/enroll` (board owner/admin) records the HOLD. The PR must be the card's authoritative recorded delivery: repository, branch and PR number come from the recorded delivery identity (`executionState.delivery`), which the delivery-identity resolver cross-checks against the card's project repository and control-plane delivery branch (the recorded branch must equal the workspace branch exactly, also case-sensitively, and the lease-agent `deliveryIdentity` write enforces the same), and its PR url must name the same GitHub repository and number. A repository changed after the delivery was recorded, a branch that is not the card's, or a PR that is only mentioned in a comment, title or document never binds. Only github.com repositories resolve; any other host is refused. The live PR must also be open, not merged and not a draft, and its head branch must be exactly the recorded delivery branch (Git refs are case-sensitive, so `Feature/X` is not `feature/x`) and its head repository must be the recorded delivery repository (a missing ref cannot be verified and is refused), read through the same warm-cache-only reader as decisions (a cold cache refuses). The binding is re-checked under the issue lock that appends the HOLD, so a delivery that changes mid-request records nothing. `raAgentId` must be an agent of the company. An identical replay answers from the ledger even if the delivery record or seat has since changed. It installs no execution policy.
- `POST /api/issues/:issueId/release-decisions` (board owner/admin) records a GO (with `evidenceDigest` and `ciRunIds`) or NO-GO. The card must be enrolled and `headSha` must equal the live PR head, otherwise 409; a head with a recorded NO-GO rejects any GO. A GO is also refused on a draft PR, when the live PR's head branch or repository is not the recorded delivery, and when the card's recorded delivery no longer matches the enrolled PR (the recorded delivery is checked under the issue lock); a NO-GO stays recordable on the enrolled PR: it skips the delivery and live-branch binding on purpose, because a veto on the enrolled PR is the safe direction. Neither enrollment nor a decision independently checks that the branch still exists (only the one PR read is made), and no base ref is certified. Shadow mode makes zero external writes, so the live head is read with an already-warm cached GitHub App token only: it never reads a secret, mints a token or touches the database. With a cold cache the decision is refused with 409 and the HOLD stays recorded. The response carries `publication: { kind: "shadow", planned }`, the status a later slice would write.
- `GET /api/issues/:issueId/release-decisions` returns the events and the durable per-head verdict: `not_enrolled`, `held`, `go` or `no_go`. A NO-GO beats a GO on the same head whatever order they arrived in.
- `executionPolicy.approvalAuthority: "release_assurance"` is accepted by the schema but refused by `normalizeIssueExecutionPolicy` unless a trusted caller passes `allowReleaseAssuranceAuthority`, so no issue create or PATCH can select it. Even then the policy must be exactly one `approval` stage with exactly one `agent` participant; any other shape is 422. `buildReleaseAssurancePolicy` is the one-stage `approval` template (only the RA seat); it is not installed yet.

Not in this slice: issuer-signature verification and key registry, the `tea-core` publisher and required `release-assurance/go` check, rulesets, repository webhooks, installing the policy on a card, the approval-versus-close separation and decomposed-parent shape, and the exclusion of RA cards from the normal publisher. Those are the later rollout steps and need their own approvals.
